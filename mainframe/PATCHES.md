# Rung-3 patch ledger (ADR-016 customization ladder)

Every change to Mainframe lands on the LOWEST rung that can express it:

- **Rung 0** — config (gateway config, env, flags). No source change.
- **Rung 1** — official extension points (extensions/skills/hooks).
- **Rung 2** — first-party additive modules in our namespace (`extensions/opzava-*`); upstream files untouched.
- **Rung 3** — source patches to UPSTREAM files. Each one MUST be logged here and is re-reviewed at every
  upstream bump (`UPSTREAM.md`). Expected near-empty. Opzava product features are NEVER rung-3 patches —
  they live in the Opzava app and use the gateway via the broker.

| # | Files touched | What / why | Upstream status |
| --- | --- | --- | --- |
| 1 | `Dockerfile` | Optional `OPZAVA_CLAUDE_CODE_VERSION` build arg installs a pinned `@anthropic-ai/claude-code` in the runtime stage, so Anthropic setup-token / claude-cli auth flows can run inside the gateway container (in-browser Claude Max connect). Default empty = upstream-identical image. | Local only; candidate to upstream as a generic extra-globals build arg. |
| 2 | `src/plugins/types.ts`, `src/plugins/provider-api-key-auth.ts`, `src/gateway/server-methods/models-auth-status.ts` | Report auth-profile OWNERSHIP over RPC. An auth method may write profiles under provider ids other than its own — OpenCode deliberately shares one key across the `opencode` (Zen) and `opencode-go` (Go) catalogs (`src/plugin-sdk/opencode.ts`) — and `models.authLogout` removes profiles by provider id, so a consumer revoking a credential cannot derive the full profile set and orphans the siblings, leaving a live key behind (Opzava #174). Adds optional `ProviderAuthMethod.ownedProfileIds`, populates it in `createProviderApiKeyAuthMethod` from the same `resolveProfileIds` the write path uses, and surfaces `ownership` (providerId -> profile ids) on the existing `models.authStatus` result. Purely additive + read-only: no provider ids in core, no change to `authLogout` semantics, and the block is optional so older clients are unaffected. | Local only; strong upstream candidate — any API consumer revoking a shared-profile credential hits this. Upstream would likely prefer a dedicated ownership/disconnect RPC; re-review at each bump and drop this patch if upstream lands an equivalent. |
| 3 | `src/commands/onboard-types.ts`, `src/cli/program/register.onboard.ts`, `src/commands/onboard-non-interactive/local/auth-choice.ts` (+ test) | Additive `openclaw onboard --credential-stdin`: read the selected auth choice's credential (API key OR token) from piped stdin instead of a flag. Opzava execs `onboard` inside the tenant's Gateway container to connect a provider, and a flag value is world-readable in that container's process list for the life of the command (Opzava #187) — the sibling write (`models auth paste-api-key`) already pipes for exactly this reason. **Why no lower rung works:** the decisive blocker is the TOKEN path — `runAnthropicSetupTokenNonInteractive` (`extensions/anthropic/register.runtime.ts`) reads `ctx.opts.token` and hard-errors, with no env or profile fallback, so a `setup-token` connect has no argv-free input at all. (Api-key choices are less absolute: core WOULD read a provider env var, but `onboard --help` names none of them and no CLI/RPC surface exposes them, so a provider-agnostic caller cannot discover which var to set; the auth-profile fallback is also opt-out-able — minimax sets `allowProfile: false`.) Skipping `onboard` for the credential write (the issue's option 3) was rejected: `onboard` also enables the provider plugin, sets `agents.defaults.model.primary`, and installs the codex/copilot runtime plugins, so dropping it changes connect semantics far beyond this fix. The patch reads stdin ONCE in the one place both credential shapes converge, then feeds it in as the highest-precedence `flagValue` for `resolveNonInteractiveApiKey` (covers every api-key provider — they all funnel through `ctx.resolveApiKey`) and as `opts.token` on the bag handed to plugin `runNonInteractive` (covers token choices). Opt-in and additive: absent the flag, every existing invocation resolves exactly as before. Fails closed on an empty pipe or a TTY. **Ops coupling:** the gateway image must be built from this fork for a provider connect to work at all — an image without the flag fails closed with `provisioning.connections.onboardCredentialStdinUnsupported` (the worker checks `onboard --help` before handing over the secret, and never falls back to argv). | Local only; strong upstream candidate — any host that onboards non-interactively on a shared machine leaks provider keys through argv today. Re-review at each bump; drop if upstream lands stdin/env credential input for `onboard`. |
