# Slice 2 design memo review (adversarial)

## Scope
`docs/plan/research/slice2-ask-admin-opzava.md` attacked against `docs/adr/ADR-003`, `ADR-004`, `ADR-005`, `ADR-007`, `ADR-009`, `docs/openclaw/gateway/protocol.md`, `docs/openclaw/gateway/operator-scopes.md`, `docs/openclaw/gateway/config-tools.md`, `packages/adapters/src/postgres/tenant-context.ts`, `packages/project-management/src/application/tasks.ts`, and `packages/identity-access/drizzle/0002_slice1e_tasks.sql`.

| # | section | severity | issue | evidence | fix |
| --- | --- | --- | --- | --- | --- |
| 1 | 6 (persistence / 0003 schema) | blocker | The migration sketch for `0003_slice2_runtime_control` is not tenant-hard without composite FKs on tenant graph edges. `assistant_turns.conversation_id`, `assistant_tool_outcomes.turn_id`, and workspace columns are free to drift independently of the owning row, so a buggy writer can attach outcomes to a foreign organization/workspace conversation and silently pierce tenant isolation assumptions even before write-through reconciliation. | `0003` draft includes plain `conversation_id`/`turn_id` references and separate `organization_id`/`workspace_id` columns, but no `REFERENCES` tying them together in the same tenant namespace in the memo. `0002` tasks migration explicitly uses the parent-child FK lock (`tasks_workspace_organization_fk`) and shows the intended pattern. (`packages/identity-access/drizzle/0002_slice1e_tasks.sql` lines 51, 82-98)
| 2 | 6 + ADR-004 | high | Idempotency in schema is under-scoped and vulnerable to cross-user collisions. `UNIQUE (organization_id, idempotency_key)` is not enough once multiple users/sessions share tenant-level keys, and there is no key tying idempotency to turn/tool-call lineage. | Memo proposes unique `(organization_id, idempotency_key)` for turns and outcomes, but no unique on `(assistant_turn_id, tool_name, tool_call_id)` and no user/scoped partition. Existing `project-management` mutators also accept commands without idempotency arguments, so retries can duplicate writes before any envelope guard exists. (`docs/plan/research/slice2-ask-admin-opzava.md` section 4, section 6; `packages/project-management/src/application/tasks.ts` at `createTask`/`updateTask`/`moveTask` signatures and implementations)
| 2b | 6 + tenant-context | medium | withTenant guardrails are insufficiently tied to DB role hardening. Slice-2 persistence design assumes RLS as a hard boundary, but `withTenant` itself does not verify the active DB role is `opzava_app`; if connection config drifts to owner/superuser role, RLS-based isolation in 0003 becomes a no-op. | `packages/adapters/src/postgres/tenant-context.ts` performs `set_config` and tenant assertion only, with no role check around transaction entry (`withTenant` lines 60-75). This can silently defeat the memo’s 0003 tenant isolation promises under misconfigured envs. | Enforce role contract at entry (`current_user` must be `opzava_app`), assert at startup and in tests, and fail CI if role drift appears.
| 3 | 6 + token/scope model | high | The memo does not harden against shared-token scope inflation at the protocol boundary. It assumes checked runtime scopes are enough, but OpenClaw operator scopes explicitly call out that shared-secret/helper auth can restore the full operator scope set even if narrower scopes are sent in request params. Any misconfigured local/admin bootstrap path that accidentally uses those auth modes re-introduces admin/pairing authority in the hot path. | `docs/openclaw/gateway/operator-scopes.md` lines 113-115 (`shared-secret` restores full scope set), plus unknown future scopes exact-match rule lines 42-43. Memo’s hot-path contract currently says only compare received scopes against expected but does not define token-auth provenance enforcement. (`docs/plan/research/slice2-ask-admin-opzava.md` section 2)
| 4 | 4 (task tool execution) + ADR-005 | high | Tool execution context is still built from caller-provided identity fields in the PM service boundary (`TaskApplicationContext` includes `orgId`, `workspaceId`, `actor.userId`, `roleKeys` directly), while the memo relies on social discipline (“ignore tenant/user ids from model”). This is a policy hole because the service API itself can be called from any actor if a caller forgets that contract. | `packages/project-management/src/application/tasks.ts` lines 197-203 build `AuthorizationSubject` from input. No extra canonicalization/rebinding to a verified session principal is performed inside the service. (`packages/project-management/src/application/tasks.ts` lines 197-203)
| 4b | 3 + config-tools + ADR-005 | medium | Static deny-list language in the memo is not enough against plugin/runtime tool drift. OpenClaw can surface plugin/plugin-origin tools through `tools.effective`; if this is not refreshed and asserted per-session at runtime, a later-added tool can inherit default allowances despite `tools.deny` not mentioning it. | `docs/openclaw/gateway/config-tools.md` lines 34-35 define `group:runtime` and line 110 states deny-wins; lines 48-54 describe plugin tools as separate tool surfaces. Memo describes only fixed tool deny list and no per-session `tools.effective` diff/check loop. (`docs/openclaw/gateway/config-tools.md`, `docs/openclaw/gateway/protocol.md`, `docs/plan/research/slice2-ask-admin-opzava.md` sections 3 and 4)
| 5 | 5 (browser streaming) + ADR-009 | high | SSE finalize race is not deterministically idempotent. Memo emits custom stream states (`assistant.final`, `failed`) but the persistence model has no state transition control (`queued/streaming/finalizing`) and no explicit one-writer lock, so duplicate completion events from reconnect and proxy retries can emit multiple durable assistant turns for one user action. | Memo relies on runtime behavior and explicit SSE finalization steps but never models finalization transitions as mutually exclusive state in one place. `assistant_turns` schema in section 6 has only conversational IDs and idempotency key with no turn-state transition constraints. (`docs/plan/research/slice2-ask-admin-opzava.md` sections 5 and 6)
| 6 | 5/4 (stream/tool error path) | major | Partial tool success race is not safely representable as one atomic outcome. The memo allows write-through task mutation + SSE stream failure, but without a per-tool execution receipt keyed to the same turn and command envelope, the UI can show failure while persisted data already reflects a success, or vice versa under reconnect retries. | SAD-path section says “command path write-through in Opzava and stream may disconnect,” but does not define atomic write-through+finalization binding by `tool_call_id`. `project-management` mutators return success/failure only on DB transaction boundary per call, with no command-level de-dup key. (`docs/plan/research/slice2-ask-admin-opzava.md` sections 5 and sad-path ledger + `packages/project-management/src/application/tasks.ts` mutators)
| 7 | 1 + protocol acceptance | major | Acceptance dishonesty remains possible: local fake-only implementation can pass all listed deliverables while never exercising real OpenClaw protocol controls (pairing persistence, scope drift, and real event semantics), and there is no hard gate preventing merge before real image tests. | Memo explicitly says fake gateway is acceptable for local proof while real acceptance is deferred, but no explicit hard CI gate is defined for blocking production/staging sign-off without real Gateway integration. (`docs/plan/research/slice2-ask-admin-opzava.md` sections 1 and 7, sad-path table)
| 8 | 2 + protocol docs | medium | Protocol misread risk: fixed client assertion (`minProtocol/maxProtocol = 4` in examples) and synthetic “expected event families” risks masking protocol-version negotiation and fail-closed unknown-event behavior in real gateway rollouts. Real clients are expected to handle negotiated protocol compatibility and protocol-specified scope/error semantics (`AUTH_SCOPE_MISMATCH`, fail-closed unknown event families, full challenge signing path). | `docs/openclaw/gateway/protocol.md` includes negotiation expectations (`minProtocol/maxProtocol`, AUTH_SCOPE_MISMATCH guidance, unknown-event fail-closed) and explicit signing/error handling requirements. Memo hardcodes a v4-only posture and does not enforce adversarial tests for version/feature mismatch handling in fake mode. (`docs/openclaw/gateway/protocol.md` lines 29-34, 760-803, 321, 799)
| 9 | 4 + ADR-007 | medium | Missing-task behavior leaks auth state. `getTask`/`updateTask`/`moveTask` all return `taskNotFound` when the task id is not returned by SQL filters; if caller-supplied IDs are rejected by context or policy, the memo path can expose existence differences instead of a uniform denial channel. ADR-007 wants hard-fail patterns for tenant context and auth mismatches. | `packages/project-management/src/application/tasks.ts` lines 508 and 665 return `taskNotFound` for missing rows. This is not coupled to a separate authorization-denial branch in the service layer. (`packages/project-management/src/application/tasks.ts` lines 508, 665, plus similar pattern in 587)

VERDICT: UNSOUND (1 blocker, 4 high, 2 major, 4 medium)
