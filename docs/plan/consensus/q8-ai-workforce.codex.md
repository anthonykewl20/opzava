# Q8 AI Workforce / AgentEmployee

**Decision.** `AgentEmployee` is Opzava's aggregate root for one AI teammate and maps 1:1 to an OpenClaw delegate agent. Shape: `AgentEmployee(id, tenantId, displayName, departmentId, personaId, autonomyTier, openclawAgentId, agentDirRef, workspaceRef, toolPolicyId, standingOrderIds, channelBindingIds, status)`. Related aggregates: `Department(id, kind, mandate, defaultTier, escalationQueue)`, `Persona(id, soul, agents, identity, userProfile?, hardBlocks, version)`, `AutonomyTier(T1_DRAFT|T2_SEND_ON_BEHALF|T3_PROACTIVE)`, `StandingOrder(id, employeeId, scope, trigger, approvalGate, escalationRule, cronRef?)`, and `Assignment(id, pmCardId, projectId, employeeId, sessionKey, runId, status, reportMessageId)`. The admin/provisioning context is the only writer to OpenClaw config: it renders `SOUL.md`, `AGENTS.md`, `IDENTITY.md`, and `USER.md`; appends/updates `agents.list[]` with unique `workspace`, `agentDir`, model, skills, tool policy, sandbox, and subagent policy; creates `bindings[]`; and provisions cron/hooks for standing orders. Opzava stores opaque OpenClaw refs, not OpenClaw rows.

**Knowledge scoping: revise Q4b.** For the workforce, employee = OpenClaw workspace/agentDir/session store. Project = Opzava-owned shared corpus/index, not a human-like brain. The earlier "project -> agent workspace" becomes "project -> `ProjectKnowledgeIndex`/shared wiki+vector corpus" behind `KnowledgeIndexPort`; it has no persona, credentials, standing orders, or channel bindings. On each assignment, the broker injects authorized project knowledge over the employee's personal memory: employee memory first, project shared vault via `memory-wiki` bridge/OKF import and `memory_search corpus=all`, then org policy corpus. Writes/captured facts land in employee memory or Opzava KB candidates, never directly in the project corpus. Cross-project leakage is blocked by `(tenantId, projectId, employeeId)` ACL and corpus revision ids.

**Delegation.** Ask Opzava is a coordinator facade/agent, not the worker. PM card or chat mention -> broker resolves tenant, project, RBAC, department, policy, and load -> creates an `Assignment` -> starts or continues the chosen employee's OpenClaw session. Slow work uses `sessions_spawn` with an allowed `agentId` or employee-owned subagent lane; the OpenClaw task ledger tracks detached work. The employee reports back as its persona into the Opzava chat/card over the broker realtime path or webhook receiver, and `Assignment` projects session/run/task state into Postgres.

**Governance defaults.** Marketing defaults to T2 for approved company-handle posting; T3 only for approved calendars/queues. Support defaults to T2 for ordinary replies, T1 for refunds, account changes, and PII export. Finance defaults to T1 for payments, invoices, bank/tax, refunds, and external sends; T2 only for internal summaries. Customer Management/CRM defaults to T1 for PII, contracts, imports/exports, and record merges; T2 for logged internal notes. T3 is reserved for monitoring, reminders, status digests, and non-mutating standing orders. Hard blocks live in persona files plus Gateway tool policy: deny runtime/filesystem mutation by default, unapproved egress, credential/admin/config tools, and plugin/exec changes outside approval.

**Biggest sad path + invariant.** Sad path: customer prompt injection convinces a Tier-2 support employee to leak CRM/finance context or issue an unauthorized refund. Invariant: no autonomous external action may cross a money, credential, PII-export, legal/contract, or tenant-admin boundary unless an Opzava approval row exists and Gateway tool policy permits the exact tool/target. Every send/tool call records actor employee, approver, project corpus revision, session/run/task ids, and channel target.

**Parity + lean ops.** One Gateway per tenant, many delegate agents inside it; no per-project processes. Scale knobs are per-agent workspaces, deterministic bindings, tool policy, cron, subagent concurrency, and Postgres read models.
