# Q12 Billing + Gateway Provisioning

**Decision.** Add a Tenant Onboarding/Provisioning bounded context that owns the signup-to-runtime SAGA. Flow: `SignupAccepted -> TenantCreated -> PlanAttached -> GatewayReserved -> GatewayStarted -> ReadyzPassed -> AdminPairingBootstrapped -> OwnerOrgSeeded -> DepartmentsAndAgentEmployeesSeeded -> RuntimeBrokerTokenStored -> ChannelWizardOpened -> Active`. The orchestrator is a platform worker in the admin/provisioning context, using a short-lived per-Gateway `operator.admin` credential; the hot broker keeps only the Q3 `operator.write` + `operator.approvals` token. Every step is idempotent on `{tenantId, provisioningJobId}` with an outbox receipt and compensator: release ports, kill container, revoke pairing token, delete seeded OpenClaw config, or cancel/refund Stripe setup intent.

**State machine + aggregates.** `Tenant.lifecycle = Provisioning -> Active -> Suspended -> Deprovisioning -> Deleted`; retry/failure belongs to `ProvisioningJob`, not tenant state. Aggregates: `Tenant`, `GatewayInstance(tenantId, runtime, host, port, tlsSha256, configPath, stateDir, workspacePath, status, leaseExpiresAt)`, `ProvisioningJob`, `Plan`, `Subscription`, `UsageMeter`, `MeterEvent`, and `Invoice`. `GatewayInstance.tenantId`, `port`, `stateDir`, and `workspacePath` are unique; reachability is the Q3 broker routing row plus expected TLS fingerprint. OpenClaw isolation follows the multiple-Gateway checklist: distinct `OPENCLAW_CONFIG_PATH`, `OPENCLAW_STATE_DIR`, workspace root, base port, and derived browser/CDP range.

**Provisioning mechanism.** Default: one rootless Docker container per tenant on a LEAN VPS, launched by Opzava's provisioner with bind mounts for config/state/workspace/auth-profile secret dirs, an env-backed Gateway token SecretRef, published loopback/private port, Docker healthcheck on `/healthz`, and readiness gate on `/readyz` plus `gateway status --require-rpc`. Lazy-start Active tenants on first broker demand; idle-stop after a quiet window while keeping mounted state. Bin-pack by CPU/RSS/disk/port range and move tenants by creating a new `GatewayInstance` then flipping routing after health. K8s pod-per-tenant/namespace and Nomad allocation-per-tenant are later adapters on `GatewayRuntimePort`; no domain change.

**Billing + limits.** Stripe sits behind `BillingPort`; Opzava owns plans, limits, invoices, and entitlement decisions. Poll/ingest OpenClaw `gateway usage-cost --json`/usage-cost RPC from session logs into `MeterEvent` with idempotency key `hash(tenant, gatewayId, agentId, window, rawUsageCost)`, roll into `UsageMeter`, then post Stripe metered usage records. Enforce limits at provisioning, broker command admission, workflow publish, and run dispatch: seats, AgentEmployee count, channels, enabled features, autonomy tiers, per-Mechanism Q11 cost budgets, hourly/daily tenant spend, and concurrency. Overage can soft-cap, require approval, or bill; dunning moves `Active -> Suspended` with a grace timer, blocks broker starts/channel sends, then `Deprovisioning -> Deleted`.

**Biggest sad path + invariant.** Worst case is an ORPHANED Gateway: billing/subscription stopped or GDPR deletion requested, but the container still runs with channel credentials and spend. Invariant: a running container must have exactly one non-deleted `GatewayInstance`, `Tenant.lifecycle = Active`, an entitlement allowing runtime, and a live provisioner lease; otherwise the reaper kills it and records a compensating outbox event. `Deprovisioning` is irreversible: stop container, revoke tokens, cancel billing, purge config/state/workspace/auth-profile dirs, delete OpenClaw channel history/memory indexes required by Q10/Q4b, and tombstone the tenant.

**Parity + lean ops.** Opzava defines lifecycle, billing, and read models; OpenClaw remains the per-tenant AI/channel runtime. This keeps pure-B parity, one operational pattern, cheap VPS density, and a clean scale path to K8s/Nomad.
