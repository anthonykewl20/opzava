# Q3 RPC Broker Auth

**1) Transport: persistent WS operator client.** The broker should keep one scoped WebSocket operator connection to each tenant Gateway and use that same connection for commands and events. The Gateway protocol is documented as the single control plane + node transport, exposes the full API, has request/response framing, idempotency keys for side-effecting methods, and is the native source for pushed events such as `session.message`, `cron`, and approval lifecycle events. Do not enable Admin HTTP RPC for the product command path in MVP: that plugin is off by default, exposes only selected methods, is described as a full operator surface for trusted host tooling that cannot use WS, and must stay on loopback/tailnet/private ingress. Keep it as an ops-only fallback, not the normal broker API.

**2) Auth: per-Gateway paired broker device token, never shared-secret/password for runtime control.** Pair one Opzava broker identity per tenant Gateway and request only `operator.write` plus `operator.approvals`. `operator.write` satisfies read needs for status, logs, usage, sessions, agents, chat, tools, and cron mutation; `operator.approvals` is required to resolve exec/plugin approvals. Do not request `operator.admin`, `operator.pairing`, or `operator.talk.secrets` for the PM/CRM control surface. Shared-secret auth is too coarse: the docs treat it as trusted operator access for that Gateway, and HTTP surfaces restore the normal full operator defaults even when narrower scopes are declared.

Channel credentials stay inside the tenant Gateway and its configured auth/secret stores, using SecretRef-style indirection where OpenClaw supports it. Opzava stores only the tenant-to-Gateway binding, endpoint, expected Gateway identity/TLS fingerprint, approved scope contract, and a vault/secret-manager reference to the paired broker device token. It should not store tenant Slack/Gmail/WhatsApp/OAuth/channel secrets in Postgres.

**3) Deployment: separate long-lived Node broker service.** Next.js serverless/edge cannot hold sockets, and a strict one-Gateway-per-tenant topology means N persistent connections with reconnect, backoff, health, and per-tenant circuit breaking. Keep the BFF route handlers stateless: they call the broker over an internal API or enqueue work; the broker owns WS lifecycle and event ingestion.

**Biggest risk:** connection fan-out failure. A Gateway outage, bad deploy, or regional network event can cause reconnect storms across many tenant sockets and starve healthy tenants unless reconnects are jittered, capped, and isolated per tenant.

**MVP vs scale:** MVP can be one broker process with an in-memory connection registry, Postgres tenant bindings, and secret-manager-backed device tokens. At scale, shard brokers by tenant hash, persist event cursors/checkpoints, add a durable event bus for UI fan-out, and rotate paired device tokens without widening scopes.
