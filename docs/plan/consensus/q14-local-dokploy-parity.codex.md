# Q14 Local Dokploy Parity

**Decision.** Use one canonical `docker-compose.yml` for Opzava, consumed locally and by Dokploy's Compose deployer; do not split the app into Swarm services. The same file may use profiles: local owns a `traefik` service, live attaches to Dokploy's existing Traefik. Identical: service names, external network `dokploy-network`, Traefik v3 label schema, router/service names, healthchecks/readiness paths, `GatewayRuntimePort` label generation, and env key names. Legitimate drift: TLS issuer, domain suffix, replicas, resource limits, backup mounts, log retention, and secret values/source. Correction to mmx: "read-scoped Docker proxy provisions containers" is impossible; provisioning needs narrowly-scoped mutation.

**Definitive service list.** Compose defines `traefik` (local profile only), `postgres`, `pgbouncer`, `redis`, `minio`, `next`, `gateway-broker`, `worker-provisioning`, `worker-projection`, `worker-metering`, and `dockerproxy-write`; optionally add `dockerproxy-read` if the broker needs Docker health/inspect. Tenant Gateway containers are not static compose services; they are reconciled runtime objects with labels produced by the Docker adapter.

**Traefik provider parity.** Tenant Gateway labels resolve identically only if the same provider reads them. On Dokploy, its core may use the Swarm provider for Dokploy-managed services, but broker-created tenant Gateways are plain Docker containers, so the Docker provider must also be enabled with `exposedByDefault=false`, `network=dokploy-network`, and label watching. Local Traefik uses the same pinned static config from repo. If Dokploy cannot guarantee those Docker-provider flags, deploy a dedicated Opzava Traefik on `dokploy-network`; do not rely on Swarm provider discovery for tenant containers. Tenant labels must include `traefik.enable=true`, `traefik.docker.network=dokploy-network`, router rule for `*.gw.${OPZAVA_DOMAIN}`, TLS cert resolver, middleware set, and service port `18789`.

**Docker socket security.** No Opzava app, broker, or worker mounts `/var/run/docker.sock`. Only `dockerproxy-write` mounts it, and only `worker-provisioning` can reach that proxy. Enable the minimum API surface required for create/start/stop/remove/inspect Gateway containers and attach networks/images/volumes; disable exec, build, plugins, secrets, swarm services/nodes, and broad system endpoints. A read-only proxy can serve broker diagnostics, but not provisioning. CI must lint compose and Dockerfiles for direct socket mounts, unexpected proxy env flags, privileged containers, and missing `opzava.gateway=true` labels.

**Topology, TLS, secrets.** Product routes are `app.${OPZAVA_DOMAIN}` for Next, `broker.${OPZAVA_DOMAIN}` for WS/API, `minio.${OPZAVA_DOMAIN}` only when exposed, and `*.gw.${OPZAVA_DOMAIN}` for per-tenant Gateways. Local uses mkcert wildcard certs and `.env`/secret files; live uses Let's Encrypt DNS-01 wildcard certs and Dokploy secrets. The keys are the same in both places; values are never committed.

**Biggest sad path + invariant.** Worst case is an orphaned tenant Gateway that remains routable after suspension/delete, with channel credentials and spend still active. Invariant: every running/routable `opzava.gateway=true` container must match exactly one `Active` tenant, non-deleted `GatewayInstance`, valid entitlement, live provisioner lease, expected network, expected labels, and expected state/config/workspace paths; the reaper stops and quarantines anything else. Lean ops stays one compose contract, one network, one label generator, one reaper, and cheap VPS density.
