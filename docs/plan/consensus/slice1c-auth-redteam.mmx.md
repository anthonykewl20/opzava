(a) Cross-tenant read via org SELECT combo
- Exploit: RESTRICTIVE select only requires current_user OR current_org. User opens withAuthenticatedIdentity (current_user set, current_org null). No PERMISSIVE org policy matches → empty set. BUT: `organizations_identity_membership_select` is a PERMISSIVE select. With current_user set and no current_org, can a user list *some* orgs they belong to? Yes — that's the intent. Does it leak orgs they don't belong to? No, the EXISTS clause binds m.user_id=current_user. OK on the explicit leakage path.
- Subtle hole: PERMISSIVE policies OR; the `organizations_tenant_isolation` PERMISSIVE matches when current_org is set even if the user has no membership in that org (e.g., current_org was set by a prior request on a pooled connection, or a stale GUC). Combined with RESTRICTIVE (current_org OR current_user), a user could SELECT * FROM organizations WHERE id=current_org for an org they aren't a member of. Not a data leak in this schema (only id/name/...), but leaks org existence/metadata and bypasses membership gating. Fix: make tenant_isolation ALSO require membership; or remove it from SELECT and let only identity_membership_select govern SELECT when current_user is set; or split policies per command (FOR SELECT use only identity_membership_select; FOR INSERT/UPDATE/DELETE use tenant_isolation + require current_org).
- OK on (a) read of memberships rows: `memberships.identity_self_select` allows SELECT where user_id=current_user AND status='active'. A user with current_user set can read their own memberships — intended. Can they read others'? No — no PERMISSIVE policy matches user_id≠current_user and current_org is null in identity path. OK.
- But: if current_org is set (post-discovery) and tenant_isolation is the policy in force, a user can SELECT from memberships where org=current_org — including rows for other users. That's a cross-user PII leak (email-ish metadata in memberships). Fix: drop `memberships.tenant_isolation` for SELECT; gate SELECT solely by `identity_self_select` + a new "memberships_admin_select" for owner/admin role_grants; or column-restrict.

(b) Spoofing/leak of app.current_user across pooled connections
- Spoofing from client: GUCs set with `set_config(..., true)` (transaction-local) cannot be set by the client via simple_protocol/extended_protocol parameter status; only via SQL inside the tx. The app sets it from the *verified* session user id server-side. OK against direct client SET, provided the driver never uses `SET LOCAL` from client-supplied strings and `search_path`/etc aren't user-controllable in that tx.
- Pool leak: `set_config('app.current_user', $1, true)` is tx-scoped. With PgBouncer in **transaction** pool mode, the GUC is scoped to the tx and reset at COMMIT/ROLLBACK — OK. With **session** pool mode, GUCs persist on the pooled backend until the client resets them; if your code path *only* sets app.current_user and never clears it, and a subsequent pooled user hits the same backend before that backend is returned, that user inherits the previous tenant's current_user. This is the classic fail-open. Even with tx-local, race window exists if you `SET LOCAL` then yield control (e.g., async/await between set and first query, or using `withAuthenticatedIdentity` reuses a connection it doesn't own). Fix: (i) pool mode = transaction only; (ii) at tx start always `SELECT set_config('app.current_user', '', false); set_config('app.current_org', '', false)`; (iii) `RESET ALL` is too broad; use `select set_config(...,'',false)` for both GUCs at tx begin in a wrapper; (iv) assert `current_setting('app.current_user', true) = expected` before running user SQL; (v) never use session-pool, and disable `SET` from clients (`options=-c default_transaction_read_only=on` is too coarse — instead use a `BEFORE CONNECT` hook in PgBouncer that runs `RESET app.current_user; RESET app.current_org;`).
- TOCT on identity read: if your "verified session" lookup itself runs in the same tx where you set current_user, fine; if it runs in a prior tx whose session-cookie was forged/replayed, you need to verify the session token server-side by re-reading auth_sessions with **no** GUCs set (table is global) and pinning the user_id before opening withAuthenticatedIdentity. Confirm there's no path where a stale/forged cookie sets current_user.
- FK-side injection: if `userId` argument is passed from request handler into `withAuthenticatedIdentity` and a bug lets a controller call it with an attacker-supplied id bypassing getSession, that's a hole. Fix: only one entry, `withAuthenticatedIdentity(fn)` with no userId param, derived solely from getSession inside the wrapper.

(c) RESTRICTIVE + PERMISSIVE combination on organizations
- SELECT: RESTRICTIVE needs (current_org OR current_user). PERMISSIVE `tenant_isolation` (id=current_org) AND PERMISSIVE `identity_membership_select` (EXISTS active membership). Both must pass one PERMISSIVE. If current_org is set to an org the user has *no* membership in, `tenant_isolation` passes (id=current_org) and `identity_membership_select` fails — but they're OR, so tenant_isolation alone lets the row through. Leak: existence + any non-membership-gated columns on organizations. Fix: drop tenant_isolation from SELECT (use `FOR SELECT` on each policy); keep it only on write.
- INSERT/UPDATE/DELETE: RESTRICTIVE requires current_org IS NOT NULL. PERMISSIVE tenant_isolation requires id=current_org. Together: can only write rows where id=current_org. Good for UPDATE/DELETE (must target own org). For INSERT: a malicious transaction that somehow set current_org to a victim's org id can create a row with id=current_org — which is the victim's org row, i.e., they can't insert *new* orgs under a victim's id (PK conflict), but they could potentially upsert metadata if any other writable column exists. Acceptable, but add `WITH CHECK (id = current_org)` explicitly to tenant_isolation on INSERT. Also: RESTRICTIVE allows writes when current_user IS NULL and current_org is set — fine, but ensure the wrapper never opens a write tx without both GUCs being server-derived.
