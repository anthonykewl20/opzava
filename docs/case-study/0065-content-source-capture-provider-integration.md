# 0065: Content Source Capture Provider Integration

Date: 2026-06-17
Status: Draft
Thread: Slices 0063 and 0064 established the Layer 7 pattern on keyword-research — a mock provider adapter conforming to the platform `ProviderAdapter` contract, plus an execution call that routes it through the platform path emitting external-call, cost, and audit operational events. This slice applies that exact pattern to the second content provider-call step, `source-capture`, proving the pattern generalizes: a second content provider call now produces a validated adapter result and the full three-event operational footprint, on a mock.

## Hook

The first provider integration could have been a one-off — keyword-research happened to fit the platform adapter shape. This slice shows it is a pattern, not a coincidence: source-capture, a different step with a different output (captured sources rather than keyword candidates), drops into the same two pieces — an adapter that wraps its existing domain producer, and an execution call that routes it through the platform's record-everything path. The same boundary, the same three operational events, the same mock-now/live-later profile. A repeatable integration shape is what keeps Layer 7 from becoming a pile of per-provider special cases.

## Product Stakes

`source-capture` produces structured, uniquely-keyed sources — the provenance pool the rest of the pipeline cites. Routing it through the platform provider boundary means each source-capture provider call now records an `ExternalCall` (what was called, when, with what idempotency key), a `CostEvent` (mock-zero here, live-shaped), and an `AuditEvent` (who triggered it, what status), exactly as keyword-research does. The adapter's profile is mode `mock` and scopes its `allowedOperations` to `source-capture`, so it cannot be used for any other operation; the execution call composes the platform's `executeProviderAdapterWithEvents` with the cost and audit event builders. The domain producer (`createMockSourceCaptureProvider`) is unchanged — the adapter wraps it and serializes its sources to JSON-safe output.

## Industry Counterfactual

The common shortcut is to integrate the second provider differently from the first — a slightly different logging shape, a different place the cost is computed, a different way the audit record is written — because there was never a pattern, only the first provider's bespoke wiring. Coverage drifts provider by provider, and the operational records stop being comparable across providers.

Opzava reuses one pattern. Source-capture's adapter and execution call are structurally identical to keyword-research's, substituting only the operation name, the profile id, and the domain producer. The operational events they emit are produced by the same platform builders, so a source-capture external-call record and a keyword-research external-call record have the same shape and the same guarantees. The integration is a template, applied; the boundary's invariants hold for every provider that passes through it.

## What We Built

We added to `src/opzava/modules/content/providers/`:

- `source-capture-adapter.ts`:
  - `SOURCE_CAPTURE_OPERATION` — `'source-capture'`
  - `createMockSourceCaptureProviderProfile()` — a validated mock `ProviderProfile` (kind `search`, mode `mock`) scoped to the source-capture operation
  - `createMockSourceCaptureProviderAdapter({ now })` — a platform `ProviderAdapter` whose `execute` parses the idea from the request input, runs the existing source-capture producer, and returns a validated `succeeded` result whose output serializes the sources to JSON-safe values (optional fields coerced to `null`)
- `source-capture-execution.ts`:
  - `SourceCaptureProviderCallInput`, `SourceCaptureProviderCallDeps`, and `runSourceCaptureProviderCall(deps, input)` — builds the validated request, runs `executeProviderAdapterWithEvents`, and appends cost and audit operational events to the sink

The content module index re-exports all four symbols.

## What We Refused To Fake

We did not invent a second integration shape; source-capture uses the identical adapter-and-execution pattern as keyword-research, so the two providers' operational records are structurally consistent.

We did not change the domain producer; the source-capture producer is reused unchanged, wrapped by the adapter.

We did not skip any of the three events; the execution call emits external-call, cost, and audit operational events, keyed to the same request and external-call ids.

We did not leak non-JSON; the adapter serializes captured sources to plain `JsonValue`, coercing optional fields to `null`, and the platform result schema enforces secret-freedom.

We did not hand-author the implementation; it was generated by the local fleet (MiMo), transcribed, reviewed (MiMo, APPROVE), and verified against the real test suite.

## The Automation Lesson

Two providers now share one integration template, which is the signal the boundary was drawn correctly: adding a provider is an adapter plus an execution call, never a new logging or accounting shape. The adversarial review surfaced a forward-looking note worth carrying — the no-op default `AbortSignal` is harmless for a mock but would silently disable cancellation if copy-pasted to a live adapter, so the live-provider slice must require an explicit signal. That is exactly the kind of latent issue to record while the pattern is still mock-only: the mock template's conveniences must not become the live template's defects. The remaining provider-call steps (article-draft, fact-check) follow the same template, with the wrinkle that their inputs are richer than a single idea — the adapter request will carry the upstream artifacts the producer needs.
