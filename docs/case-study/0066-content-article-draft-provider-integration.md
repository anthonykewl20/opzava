# 0066: Content Article Draft Provider Integration

Date: 2026-06-17
Status: Draft
Thread: Slices 0063–0065 integrated the keyword-research and source-capture provider-call steps with the platform provider boundary, each on a single-input (the idea) request. This slice integrates `article-draft`, whose producer consumes three inputs — the idea, the outline, and the source capture. It proves the adapter-and-execution pattern carries richer, multi-part provider inputs: the adapter's request input is a structured object validated field by field, and the call still emits external-call, cost, and audit operational events through the platform path on a mock profile.

## Hook

The first two provider integrations carried a single input — the idea — which made the adapter's request input trivially a single record. A real provider boundary has to carry whatever the operation needs, and article-draft needs three upstream things at once. This slice shows the pattern does not bend under that: the request input becomes a structured `{ idea, outline, sourceCapture }`, each field validated through its own contract parser before the producer runs, and the external-call/cost/audit recording is unchanged. The boundary carries the operation's real inputs, validated, without the integration shape changing.

## Product Stakes

`article-draft` is the first `llm`-kind provider in the content set (keyword-research and source-capture are `search`), and it composes the most upstream context: the idea for intent, the outline for structure, and the source capture for the sources its sections must cite. The adapter validates all three from the request input — `parseIdeaIntake`, `parseOutline`, `parseSourceCapture` — so a malformed or wrong-shaped input fails at the boundary before the producer runs, and the producer receives exactly the typed inputs it expects. The output (title, sections with cited source ids, word count) is serialized to JSON-safe values. The execution call records the same three operational events as every other provider, so an article-draft call is as observable and accountable as a keyword-research call, despite its richer input.

## Industry Counterfactual

The common shortcut is to special-case the multi-input provider — pass the three objects through some bespoke envelope, validate them inconsistently or not at all, and wire its logging differently because "it's the big one." The result is that the most context-heavy, most expensive provider call is also the least uniformly recorded and validated.

Opzava keeps article-draft on the same boundary as the single-input providers. Its request input is a strict object whose every field is validated through the same contract parsers the rest of the system uses, and its execution emits the identical three operational events through the identical platform builders. The richer input is just a richer `requestInput` value — the contract, the validation discipline, and the recording are unchanged. The expensive provider is held to the same boundary as the cheap one.

## What We Built

We added to `src/opzava/modules/content/providers/`:

- `article-draft-adapter.ts`:
  - `ARTICLE_DRAFT_OPERATION` — `'article-draft'`
  - `createMockArticleDraftProviderProfile()` — a validated mock `ProviderProfile` of kind `llm`, scoped to the article-draft operation
  - `createMockArticleDraftProviderAdapter({ now })` — a platform `ProviderAdapter` whose `execute` parses `{ idea, outline, sourceCapture }` from the request input (strict object, each field through its contract parser), runs the article-draft producer, and returns a validated `succeeded` result with JSON-safe sections (cited source ids spread into a plain array)
- `article-draft-execution.ts`:
  - `ArticleDraftProviderCallInput`, `ArticleDraftProviderCallDeps`, and `runArticleDraftProviderCall(deps, input)` — builds the request with the three-part input, runs `executeProviderAdapterWithEvents`, and appends cost and audit operational events

The content module index re-exports all four symbols.

## What We Refused To Fake

We did not relax validation for the richer input; the adapter parses the request input as a strict object and runs each field through its dedicated contract parser, so a malformed idea, outline, or source capture fails at the boundary.

We did not change the integration shape; article-draft uses the same adapter-and-execution pattern and the same three operational events as the single-input providers, despite its three-part input and `llm` kind.

We did not leak non-JSON; the drafted sections' cited source ids are spread into plain arrays, and the platform result schema enforces secret-freedom.

We did not change the domain producer; the article-draft producer is reused unchanged, wrapped by the adapter.

We did not hand-author the implementation; it was generated by the local fleet (MiMo), transcribed, reviewed (MiMo, APPROVE), and verified against the real test suite — including tests that chain the real keyword-research, source-capture, seo-brief, and outline services to produce genuine upstream inputs for the draft adapter.

## The Automation Lesson

A multi-input provider did not require a multi-input boundary — only a richer request input value, validated the same way. That is the proof the contract was the right abstraction: the thing that varies between providers is what they consume and emit, not how they are recorded or validated. Three of the four content provider-call steps now share the boundary; the fourth, fact-check, follows with a two-artifact input. Once all four are integrated, the executor can be rewired so its provider-call steps run through these recording adapters instead of the bare producers, making a full workflow run emit a complete external-call, cost, and audit trail — the operational backbone Layer 7 exists to provide.
