# packages/adapters - vendor adapters behind ports
> **Current implementation inventory (2026-07-15):** `GitHubIssueTrackerAdapter` below is the legacy OAuth/manual issue adapter, not the target GitHub App synchronization engine. PRD-019/ADR-017 require health-checked webhooks, an idempotent outbox, conflict handling, and split authority; see `docs/plan/dev-board-migration-manifest.md`.

> Part of the Opzava architecture (see ../README.md). Vocabulary: codebase-design.

## Overview
`packages/adapters` is the infrastructure layer that gives every port in `packages/ports` a concrete implementation.
It owns four adapter families (GitHub issues, object store, secrets vault, Postgres helpers) plus the Postgres connection bootstrap, tenant-GUC guard, and migration gate that the rest of the runtime builds on.
The key invariant is ADR-001 agnostic-ports: apps depend on `@opzava/adapters`, never on `@aws-sdk/client-s3`, `pg`, or `drizzle-orm` directly, and the package enforces Postgres-is-truth, RLS denial is a hard 403, and two-token boundary at the GUC seam.

## Modules

### Adapters package root - `packages/adapters/src/index.ts`
- **Interface (the seam):** the barrel re-exports `createPostgresDatabase`, `createPostgresPool`, `db`, `pool`, `GitHubIssueTrackerAdapter`, `InMemoryObjectStore`, `S3ObjectStoreAdapter`, the identity/tenant context functions, the typed DB error classes, `LocalFileSecretsVault`, and crucially `sql` from `drizzle-orm` (`packages/adapters/src/index.ts:1-50`, `:42`).
- **Behind the seam (implementation):** nothing; this is a pure re-export module with zero logic of its own.
- **Adapters:** materializes the four port adapter families consumed by the workspace; the authoritative map counts are `ObjectStorePort` = 2 adapters (real seam), `SecretsVaultPort` = 1, `IssueTrackerPort` = 1.
- **Depth:** shallow. The deletion test: removing this file does not concentrate complexity, it only forces every consumer to import concrete files, which moves the ADR-001 dependency boundary rather than deepening anything. The module is thin but the seam it materializes is load-bearing.
- **Seams:** external seam is the `@opzava/adapters` import path; re-exporting `sql` (`:42`) is the explicit trick that lets the BFF build parameterized reads without a direct `drizzle-orm` dependency, keeping the boundary intact.
- **Testing through the interface:** the interface is the test surface; this barrel has no direct test and needs none, since each exported symbol carries its own tests.
- **Deepening opportunity:** none. A barrel that exports only what the ADR-001 boundary requires is the right shape; widening it would shallow-out the consumers' seams.

### GitHub issue tracker adapter - `packages/adapters/src/github/issues.ts`
- **Interface (the seam):** `GitHubIssueTrackerAdapter implements IssueTrackerPort` (`packages/adapters/src/github/issues.ts:150`), exposing `listIssues`, `getIssue`, `createIssue`, `closeIssue` matching the four port methods (`packages/ports/src/issue-tracker.ts:48-53`). The constructor options (`:32-41`) take `repository`, a token triple (`token`/`tokenEnvName`/`vault`+`tokenRef`), optional `apiBaseUrl`, and an injectable `fetch`.
- **Behind the seam (implementation):** pagination capped at 10 pages of `per_page=100` (`:180`), pull-request entries silently skipped via `githubIssues.pullRequestSkipped` (`:104-105`, `:200`), DTO mapping with strict type guards for number/title/url/state/updatedAt that reject partial responses with `githubIssues.invalidResponse` (`:108-118`), 403/429 rate-limit detection with `retry-after` and `x-ratelimit-reset` message synthesis (`:135-148`, `:313-315`), and a pinned `x-github-api-version: 2022-11-28` header (`:303`).
- **Adapters:** `IssueTrackerPort` has 1 adapter in the authoritative map, so this is a hypothetical seam by count. The complexity it hides is real: token-source precedence, pagination, rate-limit translation, and PR-vs-issue filtering.
- **Depth:** deep. Deletion would force every caller to reimplement pagination, token precedence, rate-limit handling, and the DTO contract; the deletion test concentrates a full external protocol into one class.
- **Seams:** external seam is `IssueTrackerPort`; internal seam is `resolveToken` (`:335-360`), which evaluates `token` then `GITHUB_TOKEN` then the vault. Coupling smell: the `vault` option is typed as the concrete `LocalFileSecretsVault` (`:38`) and calls `vault.resolveSecretValue` (`:347`), a method that is NOT on `SecretsVaultPort`, so this adapter cannot accept any other vault implementation.
- **Testing through the interface:** `packages/adapters/src/github/__tests__/issues.test.ts` (70 LOC). The test surface is the port's four methods plus the token precedence and rate-limit paths; gaps: no test asserts the 10-page pagination cap or the `closeIssue` already-closed short-circuit (`:267-270`).
- **Deepening opportunity:** inject the vault as `SecretsVaultPort` plus a `resolveSecretValue` capability once that method is promoted to the port (see SecretsVaultPort finding), removing the concrete-class coupling.

### Object store in-memory adapter - `packages/adapters/src/object-store/in-memory-object-store.ts`
- **Interface (the seam):** `InMemoryObjectStore implements ObjectStorePort` (`packages/adapters/src/object-store/in-memory-object-store.ts:89`), exposing the five port methods `putObject`, `getObject`, `presignPutObject`, `presignGetObject`, `deleteObject` (`packages/ports/src/object-store.ts:59-65`). Options take `bucket` and an injectable `now` clock (`:22-25`).
- **Behind the seam (implementation):** a `Map<string, StoredObject>` keyed by object key; `collectBody` normalizes `Uint8Array`, web `ReadableStream`, and `AsyncIterable` into a buffer (`:48-77`); ETags are sha256 hex digests of the body (`:79-81`); presign produces a synthetic `memory://` URL with a computed `expiresAt` (`:166-179`); `presignGetObject` enforces existence with `objectStore.notFound` (`:151-153`), while `deleteObject` is silently idempotent on missing keys (`:158-164`).
- **Adapters:** `ObjectStorePort` has 2 adapters in the authoritative map, so this is a real seam. This adapter hides the body-shape normalization and the round-trip semantics that the S3 adapter must match.
- **Depth:** moderate. It is a test double, so deleting it removes a fake but not real transport; still, the stream-collection and ETag logic is more than a stub, so deletion would push that shape handling onto every test.
- **Seams:** external seam is `ObjectStorePort`; no internal seams beyond the private helpers. The body-normalization helpers (`isWebReadableStream`, `isAsyncIterable`, `collectBody`) are duplicated verbatim in the S3 adapter, which is a coupling cluster.
- **Testing through the interface:** `packages/adapters/src/object-store/__tests__/in-memory-object-store.test.ts` (82 LOC). The test surface is the put/get/presign/delete round trip; gap: no assertion that `deleteObject` is idempotent on a missing key, nor that `getObject` rejects a cross-bucket ref (`:120`).
- **Deepening opportunity:** extract the shared body-shape normalization (`collectBody`, `isAsyncIterable`, `isWebReadableStream`) into a small shared module so both object-store adapters test the edge cases once and shrink.

### Object store S3 adapter - `packages/adapters/src/object-store/s3-object-store.ts`
- **Interface (the seam):** `S3ObjectStoreAdapter implements ObjectStorePort` (`packages/adapters/src/object-store/s3-object-store.ts:92`), exposing the same five port methods. Options (`:25-32`) take `bucket`, `region`, optional `endpoint`, static `accessKeyId`/`secretAccessKey`, and `forcePathStyle` (defaulting true at `:101`).
- **Behind the seam (implementation):** constructs a single `S3Client` (`:98-106`); `objectBody` converts the port body union into the SDK's expected `PutObjectCommandInput["Body"]` by routing `Uint8Array`, web streams via `Readable.fromWeb`, and async iterables via `Readable.from` (`:57-67`); `bodyFromOutput` handles the four SDK body shapes: undefined (empty async generator), async iterable, web stream, and the SDK's `transformToWebStream` (`:69-90`); presign uses `getSignedUrl` with `expiresInSeconds`, and GET presign optionally synthesizes a sanitized `ResponseContentDisposition` filename (`:184-220`).
- **Adapters:** `ObjectStorePort` has 2 adapters in the authoritative map, so this is a real seam. This is the production adapter and hides the entire S3 transport, streaming conversion, and signing surface.
- **Depth:** deep. Deletion removes the only production object-store path; the streaming-body conversions and signed-URL generation are real protocol complexity that would otherwise land in callers.
- **Seams:** external seam is `ObjectStorePort`; the static-credentials constructor (`:25-32`) is an internal seam smell because it cannot source credentials from IAM or the secrets vault, narrowing deploy targets. `forcePathStyle` defaulting to true assumes MinIO-style endpoints, which is parity-correct for local docker but a latent assumption for AWS S3.
- **Testing through the interface:** none found. This is the largest test gap in the package: the production adapter with the most transport edge cases (four body output shapes, filename sanitization, error normalization) has zero tests, while the in-memory double carries the only coverage.
- **Deepening opportunity:** introduce a contract test suite keyed on `ObjectStorePort` and run it against both adapters; the port interface is already the shared test surface, so the S3 path gets real coverage without coupling tests to the SDK.

### Local file secrets vault adapter - `packages/adapters/src/secrets/local-file-secrets-vault.ts`
- **Interface (the seam):** `LocalFileSecretsVault implements SecretsVaultPort` (`packages/adapters/src/secrets/local-file-secrets-vault.ts:120`), but the exported surface is wider than the port: it adds `resolveSecretValue` (`:160-177`), `putSecret` (`:179-218`), and `deleteSecret` (`:220-234`), plus the `expectedLocalFileSecretReference` synthesizer (`:108-118`). `SecretsVaultPort` itself only declares `getRef` and `resolve` (`packages/ports/src/secrets-vault.ts:33-36`).
- **Behind the seam (implementation):** a JSON vault file with `version: 1` and a `secrets` record (`:26-29`); deterministic secret ids derived as `local-dev:<tenantId>:<purpose>:<normalizedLabel>` (`:68-70`); sha256 fingerprints of the value (`:54-56`); writes go through an atomic-ish temp-file-then-rename with `0o700` directory and `0o644` file modes (`:276-296`); reads classify ENOENT (when `allowMissing`), JSON `SyntaxError`, and unreadable-file codes into distinct `adapters.localSecrets.*` errors (`:236-274`). The privacy boundary is explicit: `resolve` returns the fingerprint but never the value (`:153-157`).
- **Adapters:** `SecretsVaultPort` has 1 adapter in the authoritative map, so this is a hypothetical seam by count. The hidden complexity is real: filesystem atomicity, reference synthesis, and read-error classification.
- **Depth:** moderate. Deletion would force callers to reimplement file I/O and reference derivation; it is a local-only adapter, so the transport is simple, but the malformed-state handling is load-bearing.
- **Seams:** external seam is `SecretsVaultPort` in name only; the real seam is the concrete class, because every caller in the repo uses `resolveSecretValue`, which is NOT on the port. Verified consumers of the concrete type or its `resolveSecretValue` method include `apps/gateway-broker/src/runtime/env.ts:162`, `apps/workers/src/provisioning/bootstrap-platform-gateway.ts:876`, `apps/workers/src/provisioning/gateway-admin-connections.ts:71` (which declares a structural `resolveSecretValue?` optional), and the GitHub adapter at `packages/adapters/src/github/issues.ts:347`. This is the strongest seam mismatch in the package.
- **Testing through the interface:** `packages/adapters/src/secrets/__tests__/local-file-secrets-vault.test.ts` (202 LOC). The test surface covers put/get/delete and read-error classification; gap: no test exercises concurrent `writeVault` temp-file races, which the `${process.pid}.tmp` suffix (`:278`) implies is a concern.
- **Deepening opportunity:** promote `resolveSecretValue` (and probably `putSecret`) onto `SecretsVaultPort` so the four real callers stop depending on `LocalFileSecretsVault` by name; this converts a hypothetical seam into a real one and unblocks a second vault adapter.

### Postgres client and lazy pool - `packages/adapters/src/postgres/client.ts`
- **Interface (the seam):** exports `createPostgresPool`, `createPostgresDatabase`, and the lazy singletons `pool` and `db` (`packages/adapters/src/postgres/client.ts:1-59`).
- **Behind the seam (implementation):** a `lazyProxy` wraps an empty target and resolves the real pool/database on first property access, binding functions to the instance (`:46-59`); the singletons are populated by `resolvePool`/`resolveDb` using `??=` (`:33-44`). `createPostgresDatabase` carries the PgBouncer contract as a structural comment: unnamed parameterized queries only, no `name`, no Drizzle `.prepare()` (`:17-24`). `application_name: "opzava-app"` is set on the pool (`:13`).
- **Adapters:** none from the authoritative port map; this is infrastructure support consumed by the tenant/identity context modules.
- **Depth:** moderate. The lazy indirection is small but load-bearing: importing the module must have zero side effects so that `next build` route collection can import the auth stack without `DATABASE_URL` set (`:28-32`). Deletion would push lazy-singleton correctness into every caller.
- **Seams:** external seam is the `pool`/`db` singletons; internal seam is `readRuntimeDatabaseUrl` from `./env.js` (`:4`). Coupling note: the PgBouncer constraint lives in a comment, not in code, so it is a convention enforced by review rather than by the type system.
- **Testing through the interface:** `packages/adapters/src/postgres/__tests__/tenant-rls.integration.test.ts` exercises the database; no unit test asserts the import-time-no-side-effect invariant, which is the actual deletion test.
- **Deepening opportunity:** add a unit test that imports the module with `DATABASE_URL` unset and asserts no connection is attempted until first property access, pinning the load-bearing laziness.

### Postgres error mapping - `packages/adapters/src/postgres/errors.ts`
- **Interface (the seam):** the error classes `ForbiddenError`, `TenantContextMissingError`, `RuntimeDatabaseRoleError`, `ConflictError`, `DatabaseOperationError`, the union `PublicDatabaseError`, the guard `isPublicDatabaseError`, and `mapDatabaseError` (`packages/adapters/src/postgres/errors.ts:1-107`). `ForbiddenError` carries `status = 403` (`:5-6`) and `ConflictError` `status = 409` (`:34-35`), so callers can map these directly to HTTP.
- **Behind the seam (implementation):** two SQLSTATE sets, forbidden `{42501, 23503}` and conflict `{23502, 23505, 23514, 23P01}` (`:1-2`); `findSqlState` walks a bounded `.cause` chain to depth 5 matching `/^[0-9A-Z]{5}$/` (`:60-76`); `mapDatabaseError` is idempotent on public errors, falls back to conflict on any `23*` class, and otherwise returns a `DatabaseOperationError` (`:88-107`).
- **Adapters:** none; this module is the translation seam that lets tenant/identity context throw typed errors instead of leaking driver noise.
- **Depth:** moderate. The mapping table is small, but the bounded cause-chain walk is real robustness against Drizzle's nested wrapping; deletion would push SQLSTATE matching into every caller of `withTenant`/`withAuthenticatedIdentity`.
- **Seams:** external seam is the typed error union and `mapDatabaseError`; consumed by `tenant-context.ts` and `identity-context.ts` at every `catch` site.
- **Testing through the interface:** exercised through `packages/adapters/src/postgres/__tests__/tenant-context.test.ts`; gap: no direct unit test for the bounded `findSqlState` walk or the `23*` class catch-all at `:102`.
- **Deepening opportunity:** none. The mapping is already the right depth; promote the cause-chain and `23*` paths into a direct unit test.

### Postgres identity context - `packages/adapters/src/postgres/identity-context.ts`
- **Interface (the seam):** `withAuthenticatedIdentity`, `assertCurrentUser`, and the types `AuthenticatedIdentityInput`, `AuthenticatedIdentity`, `IdentityTransaction` (`packages/adapters/src/postgres/identity-context.ts:74-113`, `:9-19`). `IdentityTransaction` is an alias of `TenantTransaction`.
- **Behind the seam (implementation):** `resolveIdentityFromSession` rejects empty tokens with `ForbiddenError` (`:45-47`), then in a transaction resets `app.current_user` and `app.current_org` GUCs before reading `public.auth_sessions` by token and expiry (`:33-61`). `withAuthenticatedIdentity` re-runs the GUC reset, sets `app.current_user` to the resolved userId via bound-parameter `set_config`, calls `assertCurrentUser` to confirm the DB GUC matches, then runs the caller's `fn` (`:94-113`). The DB session row is the source of truth, never the caller-supplied token claims.
- **Adapters:** none; this module is the auth side of the two-token boundary: a session token resolves to an identity and binds the user GUC that RLS policies read.
- **Depth:** deep. Session lookup, GUC reset ordering, and transaction scoping are security-critical; deletion would push a subtle, exploit-prone flow into every authenticated query path.
- **Seams:** external seam is `withAuthenticatedIdentity`; internal seams are `db`, `mapDatabaseError`, and the `TenantQueryable`/`TenantTransaction` types from `tenant-context.ts`. Coupling note: it depends on the `public.auth_sessions` table shape, which lives in `packages/identity-access`, so the adapter crosses a bounded-context boundary by raw SQL.
- **Testing through the interface:** none found. This is a significant gap for a security-critical module: the empty-token rejection, GUC reset ordering, and `assertCurrentUser` mismatch path are all uncovered by a direct test.
- **Deepening opportunity:** none structurally; the module is already deep. The real move is adding the missing direct tests for the empty-token and wrong-current-user paths.

### Postgres tenant context - `packages/adapters/src/postgres/tenant-context.ts`
- **Interface (the seam):** `withTenant`, `assertCurrentTenant`, `assertRuntimeDatabaseRole`, `assertValidTenantUuid`, and the types `TenantTransaction`, `TenantQueryable` (`packages/adapters/src/postgres/tenant-context.ts:85-109`, `:42-83`, `:17-21`). `TenantTransaction` is derived directly from the Drizzle `db.transaction` callback signature so it stays in sync with the installed version (`:17`).
- **Behind the seam (implementation):** `assertValidTenantUuid` matches the canonical UUID regex (`:10-11`, `:23-27`); `assertRuntimeDatabaseRole` queries `pg_roles` and rejects anything other than role `opzava_app`, plus any `rolsuper` or `rolbypassrls` flag (`:64-83`); `withTenant` opens a transaction, asserts the role, sets `app.current_org` via `set_config(..., true)` as a bound transaction-local parameter, then asserts the GUC round-trips before running `fn` (`:85-109`). The GUC is set only after BEGIN so it cannot leak across PgBouncer transaction-pooled connections (`:95-101`).
- **Adapters:** none from the port map; this is the RLS guard, the module that makes Postgres-is-truth and RLS-denial-is-403 actually hold at runtime.
- **Depth:** deep. Tenant scoping, runtime-role validation, and transaction-local GUCs are all load-bearing; deletion would dissolve tenant isolation into caller discipline.
- **Seams:** external seam is `withTenant`, the single integration point every tenant-scoped write must pass through; internal seams are `db` and `mapDatabaseError`. The round-trip assertion at `:101` is the seam that converts a GUC set into a verified invariant.
- **Testing through the interface:** `packages/adapters/src/postgres/__tests__/tenant-context.test.ts` (64 LOC) and `packages/adapters/src/postgres/__tests__/tenant-rls.integration.test.ts` (164 LOC). The test surface covers missing context, cross-tenant writes, and wrong-role rejection; gap: the integration test depends on a live Postgres, so the role and GUC invariants are not pinned in fast CI without the database.
- **Deepening opportunity:** none. Already deep; the move is keeping the integration test on the required CI path so the role/GUC invariants cannot silently regress.

- **Testing through the interface:** none found. The test surface is the unsafe-command rejection, the unsafe-path rejection, and the hash-drift detection; all three are deterministic and cheap to cover but currently untested.
- **Deepening opportunity:** none. Already deep; the move is a direct unit test for `forbidUnsafeMigrationCommand` and `verifyMigrationManifest` error paths, which are pure functions.

## Cross-cutting notes
- **Depth heat:** deep modules are GitHub issues, S3 object store, identity-context, tenant-context, and the migration gate/runner (5). Moderate are in-memory object store, local-file secrets vault, client, and errors (4). Shallow are env and the package root barrel (2). The deepest seams guard external protocols or security invariants; the shallowst are validators and re-exports.
- **Shared coupling and blast radius:** the Postgres helper quad (client, env, errors, tenant-context, identity-context) is a tight cluster where tenant-context and identity-context both depend on client and errors, so a change to the lazy singleton or the SQLSTATE mapping ripples into every authenticated or tenant-scoped write in the system. The object-store adapters share duplicated body-normalization logic, so a stream-handling bug would likely need two fixes.
- **Patterns observed.** RLS / withTenant: tenant-context sets the GUC as a bound transaction-local parameter and round-trip-asserts it, and identity-context mirrors this for `app.current_user`, implementing the two-token boundary at the GUC seam. Agnostic-ports: the barrel re-exports `sql` so apps never take a direct `drizzle-orm` dependency, and all four adapter families implement a `packages/ports` interface. Postgres-is-truth: the tenant/identity modules reload state from the DB session and GUCs rather than trusting caller values. The package does not carry projection-cache or tool-policy patterns; those live in `packages/runtime-control`.
- **Friction clusters.** The `SecretsVaultPort` seam is hypothetical not just by adapter count but by interface: the port omits `resolveSecretValue`, the method every real caller needs, so four call sites couple to the concrete `LocalFileSecretsVault` class. The production S3 adapter has no tests while its in-memory double carries all the coverage. The security-critical identity-context has no direct test. The PgBouncer and migration-entrypoint isolation rules are enforced by comment rather than by code.

## File map
- `packages/adapters/src/index.ts` - barrel that materializes the ADR-001 `@opzava/adapters` dependency boundary, including a re-exported `drizzle-orm` `sql` tag.
- `packages/adapters/src/github/issues.ts` - `IssueTrackerPort` adapter over the GitHub REST API (pagination, rate limits, token precedence, PR filtering).
- `packages/adapters/src/object-store/in-memory-object-store.ts` - `ObjectStorePort` test double with sha256 ETags and synthetic presign URLs.
- `packages/adapters/src/object-store/s3-object-store.ts` - production `ObjectStorePort` adapter over AWS S3 (streaming bodies, signed URLs).
- `packages/adapters/src/secrets/local-file-secrets-vault.ts` - `SecretsVaultPort` adapter backed by an atomic-ish JSON vault file; the real seam is the concrete class, which exposes `resolveSecretValue` beyond the port.
- `packages/adapters/src/postgres/client.ts` - lazy Postgres pool/database singletons with a build-time no-side-effect invariant and a PgBouncer contract.
- `packages/adapters/src/postgres/env.ts` - shallow readers validating the runtime and migration `DATABASE_URL`s.
- `packages/adapters/src/postgres/errors.ts` - typed DB error union and bounded cause-chain SQLSTATE mapping.
- `packages/adapters/src/postgres/identity-context.ts` - session-token to authenticated-identity resolution with GUC reset and the two-token boundary on the user GUC.
- `packages/adapters/src/postgres/tenant-context.ts` - `withTenant` RLS guard: runtime-role check, transaction-local tenant GUC, round-trip assertion.
- `packages/adapters/src/postgres/migration-gate.ts` - deploy-time manifest verification, hash-drift detection, and unsafe-command gate.
- `packages/adapters/src/postgres/migrate.ts` - CI/deploy entrypoint that runs the gate then applies drizzle migrations as the owner role.
