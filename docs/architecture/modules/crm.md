# packages/crm - CRM bounded context
> Part of the Opzava architecture (see ../README.md). Vocabulary: codebase-design.

## Overview
`@opzava/crm` is a workspace-scoped bounded context that owns the CRM domain model (accounts, contacts, pipelines, deals, tickets, activities) and the tenant-isolated application services that read and mutate it.
It is a pure domain-and-application package: it consumes the agnostic `AuthorizationPort` and `@opzava/adapters` tenant transactions, exposes small async `Result`-returning functions, and emits no events.
Key invariants: every public service runs `authorizeCrm` before any write, every database touch goes through `withTenant(orgId)`, every persistence table is RLS-guarded on `app.current_org_id()`, and idempotency keys replay prior writes (packages/crm/src/application/accounts.ts:290, packages/crm/src/application/contacts.ts:260, packages/crm/src/application/deals.ts:453, packages/crm/src/application/tickets.ts:260).

## Modules

### CRM package entry and domain - `packages/crm/src/index.ts`, `packages/crm/src/domain/crm.ts`
- **Interface (the seam):**
  - Entry barrel re-exports domain and application surfaces wholesale (packages/crm/src/index.ts:1-2; application barrel at packages/crm/src/application/index.ts:1-71).
  - Domain constants and union types: `crmContactLifecycles`, `crmDealStatuses`, `crmTicketStatuses`, `crmTicketPriorities`, `crmActivityKinds`, `crmActivityActorKinds` plus their derived types (packages/crm/src/domain/crm.ts:4-37).
  - Aggregate-style records: `CrmAccount`, `CrmContact`, `CrmPipeline`, `CrmPipelineStage`, `CrmDeal`, `CrmTicket`, `CrmActivity` (packages/crm/src/domain/crm.ts:39-140).
  - Parsers `parseCrmContactLifecycle`, `parseCrmDealStatus`, `parseCrmTicketStatus`, `parseCrmTicketPriority`, `parseCrmActivityKind` returning `Result<T>` with `crm.*` error codes (packages/crm/src/domain/crm.ts:152-215).
  - Invariant the caller must know: parsers reject any value outside the constant tuple; the same constant arrays feed both the parser sets and the Postgres enum definitions, so a status added to the tuple flows into both (packages/crm/src/domain/crm.ts:142-146, packages/crm/src/adapters/postgres/schema/crm.ts:32-40).
- **Behind the seam (implementation):**
  - The domain holds no behavior beyond membership-checked parsing; transition policy (e.g. only open deals can close) is NOT here, it lives in the application services.
  - `crmValidationError` is the single `DomainError` factory for the whole domain (packages/crm/src/domain/crm.ts:148-150).
- **Adapters:** none. The domain is the leaf; it depends only on `OrgId`, `WorkspaceId`, `UserId`, `DomainError`, `Result` from `@opzava/shared-kernel` (packages/crm/src/domain/crm.ts:1-2).
- **Depth:** moderate. The interface is larger than a passive DTO layer because the parsers encode the allowed-value invariant, but the records themselves carry no lifecycle behavior (deletion test: removing the file breaks typing everywhere but removes no orchestration).
- **Seams:** the broad `export *` barrel (packages/crm/src/index.ts:1-2) is the only external seam; consumers reach domain types, parsers, and all application Interfaces from one import path. Internal seam between domain and application is one-way (application imports domain, never the reverse).
- **Testing through the interface:** parsers are exercised indirectly through `packages/crm/src/__tests__/slice3-crm.integration.test.ts`. No dedicated unit test for the parser sad paths (null, wrong case, empty string) exists; they are covered only transitively.
- **Deepening opportunity:** none for the entry barrel (a deliberate thin re-export). The domain could deepen by moving deal/ticket transition rules (e.g. `reopenDeal`'s "only closed deals can reopen", packages/crm/src/application/deals.ts:911-916) into the domain as a `canTransition(from, to)` function so the rule is testable without a database.

### CRM application shared and authorization - `packages/crm/src/application/shared.ts`, `packages/crm/src/application/authorization.ts`
- **Interface (the seam):**
  - Context and DI types `CrmActor`, `CrmApplicationContext` (org+workspace+actor), `CrmApplicationDependencies` (optional `authorizationPort`) (packages/crm/src/application/shared.ts:29-42).
  - DTO read models: `CrmAccountDto`, `CrmContactDto`, `CrmPipelineDto`, `CrmPipelineStageDto`, `CrmPipelineWithStagesDto`, `CrmDealDto`, `CrmDealStageColumnDto`, `CrmListPageDto<T>`, `CrmTicketDto`, `CrmActivityDto` (packages/crm/src/application/shared.ts:44-175).
  - Error and row helpers: `crmError`, `databaseError`, `rowsFromExecuteResult`, `parseDate`, `parseNullableDate`, `stringOrNull`, `numberOrNull` (packages/crm/src/application/shared.ts:181-248).
  - Projection mappers `rowToAccountDto` ... `rowToActivityDto` that throw on unknown enum values (packages/crm/src/application/shared.ts:250-408).
  - Context and auth gates: `assertKnownIds`, `assertKnownUuid`, `authorizationSubject`, `authorizeCrm(input, action, port?)` (packages/crm/src/application/shared.ts:410-467).
  - Normalizers: `normalizeRequiredText`, `normalizeOptionalText`, `normalizeLongText`, `normalizeOptionalUserId`, `normalizeIdempotencyKey`, `normalizeCurrency`, `normalizeValueCents`, `normalizeDate`, `normalizeLimit`, `normalizeOffset` (packages/crm/src/application/shared.ts:469-601).
  - Activity writer `insertCrmActivity(tx, input, params)` (packages/crm/src/application/shared.ts:603-664).
  - The authorization adapter: class `RoleKeyCrmAuthorizationPort implements AuthorizationPort` plus singleton `defaultCrmAuthorizationPort` (packages/crm/src/application/authorization.ts:39-103).
  - Invariants the caller must know: `authorizeCrm` returns `crm.forbidden` when the port denies and passes the port error through otherwise (packages/crm/src/application/shared.ts:462-464); every normalizer returns `Result` with `crm.validation` errors, never throws; `insertCrmActivity` resolves actor user id only for `human` actors (packages/crm/src/application/shared.ts:636); `rowToContactDto`/`rowToDealDto`/`rowToTicketDto`/`rowToActivityDto` THROW (not return err) on a bad enum, so they assume the database enum is authoritative.
- **Behind the seam (implementation):**
  - `authorizeCrm` always asks the port for the `member` grant regardless of the `action` argument; the four actions (`read`/`create`/`update`/`delete`) are accepted by the port (packages/crm/src/application/authorization.ts:64-73) but `roleAllows("member", ...)` is the single role check applied to all of them.
  - The role hierarchy lives entirely in `roleAllows`: `guest` requires the literal `guest` role, `member` requires any of `owner`/`admin`/`member`, `admin` requires `owner` or `admin`, and the default branch requires `owner` (packages/crm/src/application/authorization.ts:13-29).
  - `authorizationSubject` collapses context into the repo-wide `AuthorizationSubject` shape, seeding `workspaceIds` with exactly one workspace (packages/crm/src/application/shared.ts:436-444).
  - The `uuidPattern` regex is the single source of truth for `assertKnownUuid` (packages/crm/src/application/shared.ts:179, 428-434).
  - This is where complexity concentrates: 664 LOC in `shared.ts` fuse error mapping, row projection, validation, normalization, authorization wiring, and activity insertion into one helper layer.
- **Adapters:**
  - Satisfies `AuthorizationPort` (a real repo-wide seam with 3 adapters: packages/crm, packages/project-management, packages/runtime-control); CRM contributes this 1 adapter (packages/crm/src/application/authorization.ts:39).
  - Complexity hidden: tenant/org/workspace membership checks and the role-to-grant mapping; the rest of the package never re-derives roles.
  - Consumes `AuthorizationPort`, `AuthorizationSubject` from `@opzava/ports` and `TenantTransaction`, `sql`, `mapDatabaseError` from `@opzava/adapters` (packages/crm/src/application/shared.ts:1-2).
- **Depth:** deep. The public helper surface is small relative to the behavior hidden (role mapping, projection mapping for 7 entities, 10 normalizers, UUID validation, error normalization). Deletion test: removing `shared.ts` dissolves the entire permission boundary and projection contract for the context.
- **Seams:** the authorization seam is external (repo-wide `AuthorizationPort`); `CrmApplicationDependencies.authorizationPort` is the injection point (packages/crm/src/application/shared.ts:40-42). The shared-helper seam is internal to the package; every CRUD module imports from it. Coupling note: `shared.ts` imports `defaultCrmAuthorizationPort` from `authorization.ts` (packages/crm/src/application/shared.ts:14), while `authorization.ts` imports nothing from `shared.ts`, so the dependency is one-way.
- **Testing through the interface:** `packages/crm/src/__tests__/slice3-crm.integration.test.ts` exercises `authorizeCrm` end-to-end (forbidden for non-member, tenant isolation) at lines 229 and 737. Gaps: the role hierarchy (`guest`/`admin`/`owner` branches in `roleAllows`) has no direct unit test; `RoleKeyCrmAuthorizationPort.hasTenantGrant` and `hasProjectGrant` (packages/crm/src/application/authorization.ts:76-100) appear untested; the normalizers' length and format boundaries are not asserted directly.
- **Deepening opportunity:** split `shared.ts`. It currently bundles four concerns (DTO+mapper projection, validation+normalization, error+row helpers, authorization wiring+activity writes) into 664 LOC. Extracting a `projection.ts` (DTOs + `rowTo*Dto`) and a `validation.ts` (normalizers) would shrink the helper seam and make each concern independently testable. Secondary: make `authorizeCrm` action-aware, since today `delete` and `read` pass the same `member` check, which is almost certainly too permissive for delete.

### CRM accounts, contacts, deals, tickets, and activities - `packages/crm/src/application/{accounts,contacts,deals,tickets,activities}.ts`
- **Interface (the seam):**
  - Account: `createAccount`, `updateAccount`, `getAccount`, `listAccounts` with `CreateAccountInput`/`UpdateAccountInput`/`GetAccountInput`/`ListAccountsInput` (packages/crm/src/application/accounts.ts:269, 368, 500, 531).
  - Contact: `createContact`, `updateContact`, `getContact`, `listContacts`, `listContactTimeline` (packages/crm/src/application/contacts.ts:239, 336, 463, 494, 578).
  - Deal and pipeline: `ensureDefaultPipeline`, `ensureDefaultPipelineInTx` (tx-scoped), `createDeal`, `moveDealStage`, `closeDeal`, `reopenDeal`, `updateDeal`, `listDeals` (packages/crm/src/application/deals.ts:409, 349, 432, 570, 694, 812, 935, 1038).
  - Ticket: `createTicket`, `updateTicketStatus`, `updateTicket`, `listTickets`, `getTicket` (packages/crm/src/application/tickets.ts:239, 342, 458, 547, 640).
  - Activity: `addNote` (the only public activity-facing API; the other activity kinds are emitted internally by the CRUD services) (packages/crm/src/application/activities.ts:66).
  - Internal cross-module seam: `accountInternal`, `contactInternal`, `dealInternal`, `ticketInternal`, each exposing only `selectXById` for reuse by siblings (packages/crm/src/application/accounts.ts:612-614; contacts.ts:643-645; deals.ts:1150-1152; tickets.ts:669-671).
  - Invariants the caller must know: every function takes `CrmApplicationContext` fields plus its own inputs and returns `Promise<Result<...>>`; every function runs `assertKnownIds` then `authorizeCrm` before touching the DB (e.g. packages/crm/src/application/accounts.ts:273-286); list endpoints return `CrmListPageDto` with `hasMore` computed by over-fetching by one (packages/crm/src/application/accounts.ts:597-605); `addNote` requires exactly one subject id (packages/crm/src/application/activities.ts:75-78); deal/ticket state transitions are guarded (only open deals close at packages/crm/src/application/deals.ts:734, only non-open deals reopen at packages/crm/src/application/deals.ts:840, ticket status change emits activity only when the status actually differs at packages/crm/src/application/tickets.ts:375).
- **Behind the seam (implementation):**
  - Idempotency is implemented uniformly: a pre-insert replay lookup by `(organization_id, idempotency_key)`, an `on conflict do nothing`, and a post-conflict replay fallback (packages/crm/src/application/accounts.ts:290-351; same shape in contacts.ts:260-318, deals.ts:453-551, tickets.ts:260-323).
  - Referential integrity is enforced in-application before insert: account parent must resolve and the parent chain must be acyclic within 10 hops under a per-org advisory lock (packages/crm/src/application/accounts.ts:218-267, 453-455); contact account, deal account+contact+stage, and ticket contact+account are validated via the sibling `*Internal.selectXById` helpers (packages/crm/src/application/contacts.ts:226-237, packages/crm/src/application/deals.ts:285-298, 465-495, packages/crm/src/application/tickets.ts:218-237).
  - Default pipeline provisioning is idempotent and inserts the four canonical stages (`Lead in`, `Qualified`, `Proposal`, `Negotiation`) via an `unnest` bulk insert (packages/crm/src/application/deals.ts:89, 349-407).
  - Deal lifecycle mutations use single-statement CTEs (`with updated as (...)` / `candidate ... for update`) so the read-after-write is one round trip and the optimistic transition guard is atomic (packages/crm/src/application/deals.ts:595-664, 724-787, 833-909; packages/crm/src/application/tickets.ts:368-428).
  - Projection reads compute counts via correlated subqueries on the fly: `contact_count`/`deal_count`/`ticket_count` per account (packages/crm/src/application/accounts.ts:137-157), `open_ticket_count`/`open_deal_count` per contact (packages/crm/src/application/contacts.ts:158-176), and stage-grouped columns for the deals board (packages/crm/src/application/deals.ts:1080-1143).
  - `addNote` is the cross-cutting coordination point: it routes to exactly one of the four `selectXById` helpers, derives the secondary refs (e.g. a deal's account+contact), and writes one activity row (packages/crm/src/application/activities.ts:101-181).
- **Adapters:** none directly. These services consume the CRM authorization adapter through `authorizeCrm` (packages/crm/src/application/shared.ts:446) and the tenant-transaction helper `withTenant` from `@opzava/adapters` (packages/crm/src/application/accounts.ts:1; origin packages/adapters/src/postgres/tenant-context.ts:85). They do not implement any repo-wide port.
- **Depth:** deep. The public signatures are small CRUD-shaped functions; behind them sit idempotency replay, advisory-locked cycle prevention, CTE-based atomic transitions, multi-table referential validation, and live projection assembly. Deletion test: removing any one of these modules removes a whole entity surface plus the invariants (idempotency, cycle prevention, transition guards) that the database schema does not encode.
- **Seams:** internal seams are the `*Internal.selectXById` objects, which let `activities.ts` and cross-entity validation reach sibling reads without widening the public API. External seam is the application barrel (packages/crm/src/application/index.ts:1-71). Coupling: the five files import only from `./shared.js`, `../domain/index.js`, `@opzava/adapters`, and `@opzava/shared-kernel`; `activities.ts` is the only one that imports all four sibling internals (packages/crm/src/application/activities.ts:4-7), making it the densest internal coupling point.
- **Testing through the interface:** `packages/crm/src/__tests__/slice3-crm.integration.test.ts` (795 LOC, 7 cases) covers tenant isolation+forbidden (line 229), idempotent creates (327), list pages (440), pipeline+stage movement (505), deal close/reopen/lost with conflict protection (615), ticket contact validation+status-change activity (671), and contact timeline+invalid parent (737). Gaps: `updateAccount`/`updateContact`/`updateDeal`/`updateTicket` partial-field paths are not asserted individually; `moveDealStage` to a stage on a different pipeline is not exercised; `ensureDefaultPipeline` replay-after-insert is not tested in isolation.
- **Deepening opportunity:** split the deals god-module. At 1152 LOC `deals.ts` fuses pipeline provisioning (`ensureDefaultPipeline*`, `selectDefaultPipelineInTx`, `selectStage*`), deal aggregate mutations (`createDeal`/`moveDealStage`/`closeDeal`/`reopenDeal`/`updateDeal`), and the board projection (`listDeals` with stage columns). Extracting a `pipelines.ts` would isolate the pipeline seam and let `deals.ts` shrink to aggregate lifecycle. Secondary: the repeated idempotency-replay boilerplate (pre-lookup, on-conflict, post-replay) appears verbatim four times and could fold into a shared `withIdempotentCreate` helper in `shared.ts`.

### CRM postgres schema - `packages/crm/src/adapters/postgres/schema/crm.ts`
- **Interface (the seam):**
  - Barrel re-export (packages/crm/src/adapters/postgres/schema/index.ts:1).
  - Seven tables: `crmAccounts`, `crmContacts`, `crmPipelines`, `crmPipelineStages`, `crmDeals`, `crmTickets`, `crmActivities` (packages/crm/src/adapters/postgres/schema/crm.ts:42, 98, 158, 202, 262, 356, 420).
  - Six pgEnums derived from the domain constant tuples (packages/crm/src/adapters/postgres/schema/crm.ts:32-40).
  - Two pgRoles `appRole` (`opzava_app`) and `ownerRole` (`opzava_owner`) used by every policy (packages/crm/src/adapters/postgres/schema/crm.ts:29-30).
  - Critical header invariant: the file declares itself NOT authoritative; hand-written migrations `0012+` are the real DDL contract, and this Drizzle schema exists only for query typing (packages/crm/src/adapters/postgres/schema/crm.ts:1-2).
- **Behind the seam (implementation):**
  - Every table carries the same three-policy RLS block: permissive `tenant_isolation` on `organization_id = app.current_org_id()`, restrictive `tenant_context_required` that blocks rows when no org context is set, and a permissive `owner_admin` escape hatch for the `opzava_owner` role (e.g. packages/crm/src/adapters/postgres/schema/crm.ts:76-95, repeated per table).
  - Idempotency is schema-enforced: `uniqueIndex(...organization_idempotency_key_unique)` on accounts, contacts, deals, and tickets (packages/crm/src/adapters/postgres/schema/crm.ts:61-64, 118-121, 287-290, 376-379).
  - The activity subject invariant is a check constraint requiring at least one of contact/account/deal/ticket to be non-null (packages/crm/src/adapters/postgres/schema/crm.ts:469-475), mirroring the application-layer `addNote` rule.
  - Composite organization-scoped foreign keys (e.g. `crm_deals_stage_pipeline_organization_fk`) encode the "stage must belong to the deal's pipeline" invariant at the storage layer (packages/crm/src/adapters/postgres/schema/crm.ts:318-326).
  - Read-aid indexes target the real query shapes: contact/deal/activity timeline by `occurred_at`, deal board by `(pipeline, stage, position)`, ticket queue by `(status, priority)` (packages/crm/src/adapters/postgres/schema/crm.ts:439-448, 291-297, 380-385).
- **Adapters:** none directly. This is the persistence boundary the application layer reads and writes through raw `sql` tagged templates (no Drizzle query builder is used in the application code).
- **Depth:** moderate. The tables are declarative, but the RLS policy pattern and the check constraints encode behavioral contracts (tenant isolation, activity subject presence, non-negative deal value, currency format) that the application layer relies on. Deletion test: removing the file breaks Drizzle typing and the enum derivations, but the runtime DDL contract actually lives in migrations 0012+, so the blast radius at runtime is smaller than it appears.
- **Seams:** internal to the package; consumed only by the application layer's raw SQL and by the Drizzle type system. Coupling note: the enum arrays are imported from the domain (packages/crm/src/adapters/postgres/schema/crm.ts:20-27), so the domain is the single source of truth for allowed statuses and this file mirrors them into Postgres enums.
- **Testing through the interface:** RLS and constraints are exercised end-to-end by the integration test's tenant-isolation case (packages/crm/src/__tests__/slice3-crm.integration.test.ts:229). Gaps: no test asserts the `owner_admin` escape hatch, the `tenant_context_required` restrictive policy under a missing org context, or the `crm_activities_subject_ref_check` constraint directly; the "migrations 0012+ are authoritative" claim is unverified from this package alone.
- **Deepening opportunity:** formalize the migration-versus-Drizzle split. The comment at packages/crm/src/adapters/postgres/schema/crm.ts:1-2 says schema-diff must not be run on these tables, which is a load-bearing process invariant with no mechanical guard. Either add a schema-diff exclusion config that proves the claim, or generate the Drizzle file from the authoritative migration so the two cannot drift.

## Cross-cutting notes
- **Depth heat:** deep modules are `shared.ts` (664 LOC), `deals.ts` (1152 LOC), `tickets.ts` (671 LOC), `contacts.ts` (645 LOC), `accounts.ts` (614 LOC), and `activities.ts` (186 LOC). Shallow modules are the barrels `index.ts` (2 LOC) and `domain/index.ts` (1 LOC). The domain model (`crm.ts`, 215 LOC) is moderate.
- **God-module flag:** `packages/crm/src/application/deals.ts` is the CRM god-module at 1152 LOC, mixing pipeline provisioning, deal aggregate mutation, and board projection (see deepening opportunity above).
- **Shared coupling and blast radius:** `shared.ts` is the load-bearing hub; every application module imports error helpers, normalizers, the auth gate, and the activity writer from it. A change to `authorizeCrm` or any `normalize*` ripples to all five CRUD modules. The `*Internal.selectXById` objects form a smaller, deliberate internal seam that lets `activities.ts` and cross-entity validation read siblings without exposing those reads publicly.
- **Consumers (blast radius outside the package):** `@opzava/crm` is consumed by the web CRM pages and server actions (apps/web/app/(app)/crm/{accounts,contacts,deals,tickets}/**, apps/web/lib/crm-pages.ts) and by the agent runtime surface `packages/runtime-control/src/application/crm-tools.ts`. A signature change to any exported CRM function breaks both the human UI and the assistant tool layer.
- **Patterns observed:**
  - agnostic-ports: YES. CRM consumes `AuthorizationPort` purely through the `@opzava/ports` interface and injects it via `CrmApplicationDependencies.authorizationPort` (packages/crm/src/application/shared.ts:40-42, 446-450).
  - RLS/withTenant: YES, pervasive. Every table has the three-policy RLS block; every service wraps DB work in `withTenant(input.orgId)` (e.g. packages/crm/src/application/accounts.ts:289).
  - projections-are-cache: PARTIAL. CRM reads are projection-heavy (DTOs with joined `accountName`/`stageName`/`contactName` and correlated `*_count` subqueries), but the projections are computed live per query rather than materialized and rebuildable; there is no separate projection table to rebuild.
  - tool-policy-first: NOT APPLIED HERE. CRM gates on workspace role keys (`owner`/`admin`/`member`) via `AuthorizationPort`, not on tool policy. Tool policy is the runtime-control layer's responsibility around `crm-tools.ts`.
  - two-token boundary: NOT IN SCOPE. The gateway-broker hot path (`operator.write`+`approvals`) versus workers admin path (`operator.admin`) is enforced upstream of CRM; CRM is workspace-scoped application code that trusts the caller-established tenant context.
- **Friction clusters:** (1) `shared.ts` bundles four unrelated concerns behind one import path; (2) `deals.ts` is a 1152 LOC god-module; (3) `authorizeCrm` is action-blind, applying the same `member` check to `read` and `delete` (packages/crm/src/application/authorization.ts:73); (4) the Drizzle schema disclaims authority over the DDL with no mechanical guard against drift (packages/crm/src/adapters/postgres/schema/crm.ts:1-2); (5) `rowTo*Dto` mappers throw on bad enums rather than returning `Result`, so a corrupt enum value surfaces as a thrown `databaseError` instead of a typed validation failure.

## File map
- `packages/crm/src/index.ts` - package barrel; re-exports domain and application surfaces.
- `packages/crm/src/application/index.ts` - application barrel; re-exports all public service functions, input types, and the authorization adapter.
- `packages/crm/src/domain/crm.ts` - domain constants, union types, entity records, and enum parsers.
- `packages/crm/src/application/shared.ts` - DTO read models, row mappers, error/row helpers, validation normalizers, the `authorizeCrm` gate, and `insertCrmActivity`.
- `packages/crm/src/application/authorization.ts` - `RoleKeyCrmAuthorizationPort`, the CRM adapter for the repo-wide `AuthorizationPort` seam, plus `defaultCrmAuthorizationPort`.
- `packages/crm/src/application/accounts.ts` - account CRUD plus acyclic-parent validation under an advisory lock; exports `accountInternal`.
- `packages/crm/src/application/contacts.ts` - contact CRUD, account validation, and contact timeline read; exports `contactInternal`.
- `packages/crm/src/application/deals.ts` - default pipeline provisioning, deal aggregate lifecycle (create/move/close/reopen/update), and board projection; exports `dealInternal` and `ensureDefaultPipelineInTx`.
- `packages/crm/src/application/tickets.ts` - ticket CRUD, status-transition guard with activity-on-change, priority-ordered listing; exports `ticketInternal`.
- `packages/crm/src/application/activities.ts` - `addNote` cross-entity activity writer; the coordination point across the four `*Internal` selectors.
- `packages/crm/src/adapters/postgres/schema/crm.ts` - seven CRM tables, six pgEnums, and the per-table RLS policy block; non-authoritative Drizzle mirror of migrations 0012+.
- `packages/crm/src/adapters/postgres/schema/index.ts` - schema barrel.
- `packages/crm/src/__tests__/slice3-crm.integration.test.ts` - integration coverage for tenant isolation, idempotency, listing, pipeline/stage movement, deal transitions, ticket validation, and timeline.
