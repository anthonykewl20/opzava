# apps/mcp-server - hosted MCP tool registry
> **Current implementation inventory (2026-07-15):** The `opzava_tasks_*` tools and `tasks:read`/`tasks:write` scopes below are real legacy APIs. Target Dev Board tools must be version/gate/lease aware under PRD-019/ADR-017; this document does not claim that migration is built.

> Part of the Opzava architecture (see ../README.md). Vocabulary: codebase-design.

## Overview
`apps/mcp-server` is a local stdio MCP server that exposes Opzava task-card tools to an external agent client (today only Claude Code) on behalf of a human user.
It is the on-behalf-of seam for AI-assisted task authoring: a user issues a short-lived link token from the web app, the server verifies that token, derives the linked principal, and registers only the task tools that principal's scopes permit.
The key invariant is that authority is link-token driven: tenant, workspace, user, and actor come exclusively from the verified `LinkTokenPrincipal`, and any caller-supplied authority fields in tool arguments are accepted by the schema but silently discarded before reaching `@opzava/project-management`.

## Modules

### MCP bootstrap and hosted server - `apps/mcp-server/src/index.ts`, `apps/mcp-server/src/server.ts`
- **Interface (the seam):** `[ENTRY] createOpzavaMcpServer(options): Promise<OpzavaMcpRuntime>` (`apps/mcp-server/src/server.ts:72`); `[TYPE] OpzavaMcpRuntime` ({ server, principal, toolNames }, `apps/mcp-server/src/server.ts:49`); `[TYPE] OpzavaMcpServerOptions` (`apps/mcp-server/src/server.ts:42`); plus the module auto-start when `apps/mcp-server/src/index.ts` runs as the entrypoint (`apps/mcp-server/src/index.ts:13`).
  Ordering invariant: token read -> verify -> scope-gated registration -> runtime return; verification failure throws the `DomainError` from `verifyLinkToken` (`apps/mcp-server/src/server.ts:78`), so a caller never receives a runtime with a bad principal.
  Error mode: a missing token throws `mcp.linkTokenMissing` (`apps/mcp-server/src/server.ts:59`); a revoked/expired/invalid token re-throws the identity-access error verbatim (`apps/mcp-server/src/server.ts:79`).
- **Behind the seam (implementation):** `readLinkToken` resolves the token from `options.linkToken`, then `options.env.OPZAVA_LINK_TOKEN`, then `process.env.OPZAVA_LINK_TOKEN` (`apps/mcp-server/src/server.ts:55`).
  `hasScope(principal, "tasks:read" | "tasks:write")` (`apps/mcp-server/src/server.ts:68`) gates registration: `tasks:read` registers only `opzava_tasks_list` and `opzava_tasks_get`; `tasks:write` registers the ten write tools (`apps/mcp-server/src/server.ts:90`, `apps/mcp-server/src/server.ts:114`).
  Each tool is registered with MCP annotations: read tools carry `readOnlyHint: true, openWorldHint: false`; write tools carry `destructiveHint: false, openWorldHint: false` and per-tool `idempotentHint` for toggle/reorder/mark-read/due-set/watchers-set (`apps/mcp-server/src/server.ts:97`, `apps/mcp-server/src/server.ts:121`, `apps/mcp-server/src/server.ts:151`).
  The handler closures capture the principal at registration time, so authority is fixed for the life of the runtime and cannot drift per call.
  `apps/mcp-server/src/index.ts` is a thin entrypoint shim: it wires `StdioServerTransport` to `runtime.server.connect` (`apps/mcp-server/src/index.ts:10`), re-exports `createOpzavaMcpServer` and the option/runtime types (`apps/mcp-server/src/index.ts:5`), and detects entrypoint status by `import.meta.url.endsWith(process.argv[1])` (`apps/mcp-server/src/index.ts:13`).
- **Adapters:** none consumed and none satisfied; this module wires the MCP SDK `McpServer` (`apps/mcp-server/src/server.ts:84`) and the project-management service map from `apps/mcp-server/src/tools.ts`.
  It calls `verifyLinkToken` from `@opzava/identity-access` directly (`apps/mcp-server/src/server.ts:3`), not through any repo `AuthPort`; per the authoritative map, `AuthPort` has 1 adapter today (hypothetical, real by design), and the MCP server is not behind it.
  `OpzavaMcpServerOptions.verifyToken` (`apps/mcp-server/src/server.ts:45`) and `OpzavaMcpServerOptions.taskServices` (`apps/mcp-server/src/server.ts:46`) are the two test-injection seams.
- **Depth:** moderate by the deletion test.
  Delete `index.ts` and only the stdio launcher is lost; delete `server.ts` and the scope-gated registration contract vanishes, which is the live behavior, so `index.ts` is shallow process wiring wrapped around a moderate `server.ts`.
  The complexity concentrates in the scope-to-tool-set mapping and the capture-at-registration authority invariant, both small surfaces.
- **Seams:** internal seam to `apps/mcp-server/src/tools.ts` (consumes schemas, handler factories, `readToolNames`/`writeToolNames`, `defaultTaskServices`, `descriptionForTool`); external seam to `@opzava/identity-access` for `verifyLinkToken`/`LinkTokenPrincipal`/`VerifyLinkTokenInput` and to `@modelcontextprotocol/sdk` for `McpServer`.
  The server-name/version string `"opzava"` / `"2026-07-03.slice2.5b"` (`apps/mcp-server/src/server.ts:85`) is a frozen capability tag a client can pin.
- **Testing through the interface:** the test surface is `createOpzavaMcpServer` plus the linked `McpServer`, exercised over an `InMemoryTransport` pair in `apps/mcp-server/src/__tests__/mcp-server.integration.test.ts:128`.
  Existing coverage: read-only token lists exactly two read tools and rejects `opzava_tasks_create` (`apps/mcp-server/src/__tests__/mcp-server.integration.test.ts:267`); create + idempotent retry returns the same task id and writes under the token principal (`apps/mcp-server/src/__tests__/mcp-server.integration.test.ts:291`); a revoked token rejects startup with `identityAccess.linkTokenRevoked` (`apps/mcp-server/src/__tests__/mcp-server.integration.test.ts:428`).
  Gaps: no negative test that caller-supplied `tenantId`/`workspaceId`/`userId` arguments are ignored, and no test for the entrypoint `main()` path in `apps/mcp-server/src/index.ts`.
- **Deepening opportunity:** none for `server.ts` as a composition root, but see the registry module below for the substantive refactor candidate.

### MCP task tool registry - `apps/mcp-server/src/tools.ts`
- **Interface (the seam):** `[TYPE] OpzavaMcpTaskServices` (`apps/mcp-server/src/tools.ts:43`), a structural typedef over fourteen `@opzava/project-management` functions; `[TYPE] OpzavaMcpToolName` (`apps/mcp-server/src/tools.ts:41`); `[TYPE] ToolResultPayload<T>` (`{ ok: true, viaClient: "claude-code", result: T }`, `apps/mcp-server/src/tools.ts:60`); `[TYPE] ToolErrorPayload` (`{ ok: false, code, message }` with `code: "forbidden" | "not_found" | "invalid_args" | "failed"`, `apps/mcp-server/src/tools.ts:66`); `[ENTRY] defaultTaskServices` (`apps/mcp-server/src/tools.ts:72`); twelve Zod schemas (`listTasksSchema` ... `setWatchersSchema`, all `.strict()`, `apps/mcp-server/src/tools.ts:108` onward); twelve `[HANDLER]` factories `(principal, services?) => async (args) => ToolResponse` (`apps/mcp-server/src/tools.ts:356` onward); plus `descriptionForTool` and the `readToolNames`/`writeToolNames` constants.
  Invariants a caller must know: every handler ignores any caller-supplied authority field and routes exclusively through `taskContext(principal)` (`apps/mcp-server/src/tools.ts:233`); a successful payload always carries `viaClient: "claude-code"`; a failed payload's `code` is a coarse public category, not the internal `DomainError.code`.
- **Behind the seam (implementation):** this is where the MCP surface's complexity concentrates.
  `taskContext(principal)` projects the principal into `{ orgId, workspaceId, actor: { userId, roleKeys } }` (`apps/mcp-server/src/tools.ts:233`), and every handler spreads it ahead of any caller-supplied argument, so `optionalAuthorityFields` (`tenantId`, `organizationId`, `orgId`, `workspaceId`, `userId` at `apps/mcp-server/src/tools.ts:95`) are accepted for schema-friendliness but never forwarded.
  `publicCode(error)` (`apps/mcp-server/src/tools.ts:253`) maps an internal `DomainError.code` to a public bucket via substring matching (`includes("forbidden")`, `includes("NotFound")`/`"notFound"`, `includes("invalid")`/`"Malformed"`, else `"failed"`).
  `resultResponse` / `okResponse` / `errorResponse` (`apps/mcp-server/src/tools.ts:241`, `apps/mcp-server/src/tools.ts:269`, `apps/mcp-server/src/tools.ts:282`) emit both `content` (text JSON) and `structuredContent` so a client can read either.
  `createToolHandler` defaults `provenanceSource` to `"claude-code"` (`apps/mcp-server/src/tools.ts:400`).
  `updateToolHandler` (`apps/mcp-server/src/tools.ts:411`) does a read-then-update because `updateTask` cannot change status: it fetches the task, applies field updates, and if the caller's requested `status` differs from the updated task's status it calls `moveTask` with the updated `position` to preserve board ordering.
  `listToolHandler` (`apps/mcp-server/src/tools.ts:356`) loads tasks via `taskContext` only, then applies the `status` filter and `limit` (default 20, max 50) client-side.
  `descriptionForTool` (`apps/mcp-server/src/tools.ts:325`) always appends `skillGuidance` directing the agent to the `opzava-task-authoring` skill, and the four create-family tools additionally append `createIdempotencyGuidance` urging a stable `idempotencyKey` for at-least-once safety (`apps/mcp-server/src/tools.ts:89`, `apps/mcp-server/src/tools.ts:92`).
  All write schemas that mutate state accept an optional `idempotencyKey` (max 160 chars) which is forwarded to project-management for dedupe.
- **Adapters:** none satisfied; consumes `@opzava/project-management` (fourteen command functions and the `TaskDto`/`CardDetailDto`/`TaskStatus`/`taskStatuses`/`taskPriorities` types, `apps/mcp-server/src/tools.ts:1`) and `@opzava/identity-access` (type-only `LinkTokenPrincipal`, `apps/mcp-server/src/tools.ts:25`).
  `OpzavaMcpTaskServices` is a port-shaped interface with exactly one adapter (`defaultTaskServices`), so by the two-adapters rule it is a hypothetical seam today; its real job is the test-injection surface, not a swap point.
  No `ConnectionsProvisioningPort`, `AuthorizationPort`, or other repo port is consumed here.
- **Depth:** deep by the deletion test.
  Delete this module and the entire MCP command surface, validation, idempotency-forwarding, authority projection, result shaping, and public error mapping vanish; the surface is twelve tools but the interface a caller sees is one consistent `{ ok, viaClient, result } | { ok: false, code, message }` envelope plus a scope-gated tool list.
  The file is `577 LOC` (one file) and is the on-behalf-of seam for the whole server.
- **Seams:** internal seam consumed by `apps/mcp-server/src/server.ts` (schemas + handler factories + tool-name constants + descriptions); external seam to `@opzava/project-management` via `OpzavaMcpTaskServices`, and to `zod` for schema definition.
  Coupling note: the `viaClient: "claude-code"` literal is hardcoded in the success payload (`apps/mcp-server/src/tools.ts:62`) and mirrored by the `provenanceSource ?? "claude-code"` default (`apps/mcp-server/src/tools.ts:400`) and by `linkTokenClientId = "claude-code"` in `packages/identity-access/src/application/link-tokens.ts:20`, so adding a second client touches all three.
- **Testing through the interface:** the test surface is each handler factory invoked through the connected MCP client in `apps/mcp-server/src/__tests__/mcp-server.integration.test.ts`.
  Existing coverage exercises create, step-create, comment-add, and quality-check-add with idempotent retries (`apps/mcp-server/src/__tests__/mcp-server.integration.test.ts:291`) and a DB-row assertion via `withTenant` (`apps/mcp-server/src/__tests__/mcp-server.integration.test.ts:336`).
  Gaps: no handler-level test for the read-then-`moveTask` branch of `updateToolHandler` (`apps/mcp-server/src/tools.ts:441`), no test that `publicCode` classifies each `DomainError.code` bucket correctly, no test that `listToolHandler` enforces the default-20/max-50 limit, and no test asserting caller-supplied authority fields are dropped.
- **Deepening opportunity:** the `publicCode` substring matcher (`apps/mcp-server/src/tools.ts:253`) is the one shallow spot in an otherwise deep module: it relies on `includes("forbidden")` / `includes("NotFound")` / `includes("invalid")` against free-form `DomainError.code` strings, so a renamed code silently degrades to `"failed"` and leaks nothing but loses fidelity.
  Replace it with an explicit code-to-bucket map keyed on the actual `DomainError.code` literals project-management emits (or have those packages export a typed error enum) so the mapping is checkable rather than heuristic; this is a small, in-file refactor that makes the public error contract provable.

## Cross-cutting notes
- Depth heat: one deep module (`tools.ts`, 577 LOC) carries the whole MCP behavior surface; one moderate module (`server.ts`, 219 LOC) does scope-gated registration; one shallow shim (`index.ts`, 21 LOC) does stdio wiring.
  No god-module here; the deepest file is well under the workers' multi-thousand-LOC provisioning modules.
- Shared coupling and blast radius: the hardcoded `"claude-code"` client identity is load-bearing in three places (`apps/mcp-server/src/tools.ts:62`, `apps/mcp-server/src/tools.ts:400`, `packages/identity-access/src/application/link-tokens.ts:20`), and a rename or second client would ripple across all three; the MCP server also pins `@modelcontextprotocol/sdk` 1.29.0 (`apps/mcp-server/package.json`).
- Patterns observed: tool-policy-first is enforced as scope-gated registration (a `tasks:read` token literally cannot see write tools in `tools/list`, `apps/mcp-server/src/server.ts:90`); the on-behalf-of authority projection (`taskContext(principal)`) is the ACL discipline equivalent of `withTenant`/RLS for the MCP path, since every project-management call is scoped to the principal's org and workspace; projections-are-cache is respected because the MCP tools write through project-management's command layer, not against projections.
  The two-token boundary does not cross this server: it consumes only the link-token (user-issued, short-lived, `tasks:read`/`tasks:write` scopes per `packages/identity-access/src/application/link-tokens.ts:21`), never the operator device tokens, so it sits entirely outside the gateway-broker hot path.
- Friction clusters: `publicCode` substring matching (`apps/mcp-server/src/tools.ts:253`) is the only brittle spot; `optionalAuthorityFields` accepted-but-ignored fields (`apps/mcp-server/src/tools.ts:95`) are intentional anti-confusion but mean the schemas validate fields that have no effect, which is mild dead weight; the `verifyLinkToken` direct dependency means the MCP server will not automatically benefit from a future `AuthPort` second adapter unless it is migrated behind that port.

## File map
- `apps/mcp-server/src/index.ts` - stdio entrypoint; re-exports `createOpzavaMcpServer` and wires `StdioServerTransport` on auto-start.
- `apps/mcp-server/src/server.ts` - reads and verifies the link token, then scope-gates MCP tool registration onto a `McpServer`; returns `OpzavaMcpRuntime`.
- `apps/mcp-server/src/tools.ts` - the MCP task command surface: twelve Zod schemas, twelve handler factories, the `OpzavaMcpTaskServices` typedef, the principal-based authority projection, and the public error envelope.
- `apps/mcp-server/src/__tests__/mcp-server.integration.test.ts` - integration tests over an in-memory MCP transport against a real Postgres tenant fixture.
- `apps/mcp-server/package.json` - declares the `@opzava/mcp-server` private workspace package, MCP SDK 1.29.0, and the build/typecheck/test scripts.
