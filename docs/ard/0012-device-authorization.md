# ARD 0012 — Device Authorization & Persistent Reliable Connection

- **Status:** Accepted
- **Date:** 2026-06-24
- **Relates to:** ARD 0011 (single-orchestrator execution model — the `claimed_at` lease and single-active-writer lock that bound the revoked-token window and protect the rotation race); ARD 0006 (Postgres compatibility — the path to true multi-writer scale and inter-replica rotation correctness); ARD 0007 (engine separation & surface unification — the runner as canonical execution path); ARD 0008 (secret storage & resolution — `SecretReference`, no embedded secrets, hashes-at-rest); ARD 0009 (realtime chat transport — the SSE cursor reused for revocation broadcast); `docs/architecture/orchestration-hardening/MASTER-PLAN.md` (Track D — device-auth; the fused `resolveDeviceToken` cascade branch is task B1b, depends on D2)
- **Supersedes (local-store framing):** none. This is the first device-auth ARD.

## Context

Opzava authenticates its agent tools — the MCP server (`scripts/mc-mcp-server.cjs`), the CLI (`scripts/mc-cli.cjs`), and the TUI (`scripts/mc-tui.cjs`) — through two inherited mechanisms, both of which are inadequate for a self-hosted control plane whose headline value is cost attribution and whose threat model includes a co-located process or a stolen laptop disk:

1. **A single global `API_KEY`** that resolves to `role: 'admin'` unconditionally (`src/lib/auth.ts:487-502`). It is long-lived, never rotates, has no stolen-token detection, and is the credential the CLI writes to disk.
2. **Agent-scoped `agent_api_keys`** (`auth.ts:505-554`) — a genuine least-privilege improvement, but still a static bearer with no rotation, no browser-driven human approval, and no per-device revocation.

The CLI persists the operator profile (API key + session cookie) as cleartext JSON via `fs.writeFileSync` with **no mode argument** — created `0o644` (`mc-cli.cjs:130`), world/group-readable by any co-located process. `auto-credentials.ts:46` already demonstrates the correct `0o600` discipline; the CLI does not follow it. The MCP server collapses every HTTP error to a single opaque `Error: <message>` (`mc-mcp-server.cjs:82`), and its SSE client (`mc-cli.cjs:207` `sseStream`) parses only `data:` lines and **ignores `id:`** (`:252`), so it cannot resume after a connection drop even though the server-side cursor is production-grade.

The single identity-resolution seam is `getUserFromRequest(request): User | null` (`src/lib/auth.ts:435`). It cascades proxy-header → session-cookie → global API key → agent-scoped API key → plugin hook (`_authResolverHook`, `auth.ts:557-560`) → `null`. Every proven primitive a device-authorization design needs already lives here: `safeCompare` (timing-safe + dummy buffer, `:43-54`), sha256 `hashApiKey`/`hashSessionToken` (`:634-640`), `deriveRoleFromScopes` admin>operator>viewer (`:652`), `requireRole` (`:668`), `randomBytes(32)` (`:166`). The `agent_api_keys` table (migration `040`, `migrations.ts:1224`) is the structural twin of a device-token table; the `access_requests` approval queue (`src/app/api/auth/access-requests/route.ts`) is the structural twin of a device-approval leg; the `client_message_id` partial-unique-index idempotency precedent (migration `054`, `migrations.ts:1493`) is the structural twin of an `Idempotency-Key` mutation-retry guarantee.

**Topology.** The target deployment is the local-agent-tool → cloud-Dokploy origin: agent tools run on a developer machine (or in CI) and call the Opzava REST surface over the operator's Dokploy origin, terminated by Traefik TLS. The agent client is a **public client** (RFC 6749 §2.1) — it cannot hold a client secret. The MCP 2025-06-18 spec says stdio servers SHOULD NOT follow the auth spec and should retrieve credentials from the environment. A stdio MCP shim spawned by Claude Code/Desktop as a subprocess therefore has **no TTY** and cannot prompt — which rules out passphrase-based local encryption, because a fail-closed passphrase either silently breaks every cold-start-after-reboot or collapses to an env-key path anyway.

RFC 8628 (OAuth 2.0 Device Authorization Grant) is purpose-built for exactly this: a device with limited input capability obtains authorization by displaying a short user code and polling a token endpoint while a human approves in a browser on a second device. Opzava acting as **both** its own OAuth Authorization Server and its own Resource Server on its existing origin requires no new infrastructure — Traefik TLS, the `__Host-` Secure cookie, and the realtime SSE substrate are all already in production.

## Decision

Opzava acts as **both** its own OAuth 2.0 Authorization Server and Resource Server, issuing **RFC 8628 device-authorization grants** to public-client agent tools. The full design is implemented in MASTER-PLAN Track D (tasks D1–D7); this ARD records the architecture contract that those tasks must honor. The decisive, final calls:

### D1 — Tokens, entropy, and TTLs

Opaque high-entropy bearers (**not** JWTs — there is no jose/jsonwebtoken dependency; sessions are already opaque random tokens). Access = `mc_dt_` + `randomBytes(32).toString('hex')` (256 bits), **8h** TTL (`28800s`). Refresh = `mc_rt_` + `randomBytes(32).toString('hex')`, **30d** absolute cap (`15552000s`) — capped, never sliding beyond it (RFC 6749 §10.4). `device_code` = `randomBytes(32)` (≥128 bits, RFC 8628 §5.2, never displayed). `user_code` = 8 chars from the base-20 confusable-free set `BCDFGHJKLMNPQRSTVWXZ` (~34.5 bits), formatted `XXXX-XXXX`, canonicalized dash-stripped + uppercased before DB lookup. Both codes expire in `900s` (RFC 8628 §3.2). `rotation_chain_id` is an opaque UUID tying one device's lineage of refresh tokens for family-wide revocation; `rotation_seq` is a per-chain monotonic counter.

**8h, not 1h.** A 1h access TTL multiplies refresh churn 24x, multiplying rotation-race exposure (the single most likely subtle-bug surface) and DB write load, for marginal leaked-token benefit over an 8h bound plus near-real-time revocation. The 8h bound is the decisive choice.

### D2 — Strict rotation, stolen-token detection, and CHAIN-LEVEL revocation

Every refresh issues a new access **and** refresh token; the presented refresh token is marked `rotated_at` and **retained** (not deleted — RFC 6749 §10.4 "invalidated but retained"). A refresh request presenting a token whose `rotated_at IS NOT NULL` with `rotation_seq < max(rotation_seq)` for the chain is a confirmed breach → **family-wide revocation** of the entire `rotation_chain_id` + a `security.event` severity=critical broadcast (`event-bus.ts:34`, `realtime-events.ts:94`).

**Revocation is CHAIN-LEVEL, not row-level (GRILL-2 red-team correction).** `resolveDeviceToken` rejects **any** access token whose `rotation_chain_id` has **any** row with `revoked_at IS NOT NULL`, not merely the row whose `access_token_hash` matched. Rationale: when an attacker steals a refresh token and refreshes *before* the operator's revoke, the rotation creates a **new row in the same chain** with `revoked_at IS NULL`. Row-level revocation would honor the attacker's new access token for up to 8h; chain-level revocation kills it immediately because the chain is revoked. This is the default and the correctness property — it is **not** gated behind an opt-in knob.

The `MC_DEVICE_INSTANT_REVOKE=1` denylist is an **optional performance optimization** (avoids the chain-join per request by materializing `revoked_access_tokens`), not the primary mechanism. Its table **must** be created by migration `058` (see D5) — the denylist is referenced by D2/D3/D4 acceptance criteria and a missing table would runtime-fail the kill-switch.

### D3 — Three-layer rotation-race guard with SERVER-SAFE, ATOMIC disambiguation

Behind Traefik sticky sessions (`docker-compose.dokploy.yml:101` — a performance hint, **not** a correctness guarantee), a refresh POST can land on replica B while the prior rotation happened on replica A. The conditional UPDATE is the cross-instance lock (SQLite serializes writers), and the disambiguation must be **atomic** — embedded in the UPDATE predicate, not a separate read-after-UPDATE that can observe a stale snapshot.

```
UPDATE device_tokens
   SET refresh_token_hash=?, access_token_hash=?, rotation_seq=rotation_seq+1, rotated_at=now
 WHERE rotation_chain_id=? AND refresh_token_hash=?
   AND revoked_at IS NULL AND rotated_at IS NULL
   AND rotation_seq=(SELECT MAX(rotation_seq) FROM device_tokens WHERE rotation_chain_id=?)
```

- `changes()===1` → **winner**: issue the new token pair.
- `changes()===0` → **re-read the chain and disambiguate by `rotation_seq`**:
  - presented hash's `revoked_at IS NOT NULL` → `401 invalid_grant` (already revoked, idempotent).
  - presented hash's `rotated_at IS NOT NULL` **and** `rotation_seq == max(rotation_seq)` → **legit concurrent loser** (two mc shims, a retrying proxy): return `409 already_rotated` with the **current valid token's metadata**, **not** a new pair and **not** a revoke.
  - presented hash's `rotated_at IS NOT NULL` **and** `rotation_seq < max(rotation_seq)` → **genuine reuse**: family revoke the chain + `security.event` severity=critical.

This is the corrected design. The original v1 framing (`changes()===0 → reuse → family revoke`) would have **false-revoked** an entire family on a legitimate concurrent retry, locking the user out. The `MAX(rotation_seq)` subquery runs **inside** the UPDATE statement so SQLite serializes the predicate and the write as one atomic point; a separate disambiguation read is only taken on the loser branch and must be read-only and idempotent (re-triggering chain revocation on an already-revoked chain is a safe no-op). A **multi-process** concurrency test (two `better-sqlite3` handles to the same file with `busy_timeout`, replaying seq-1 across all orderings) — not a single-connection in-memory test — is the acceptance gate for this task. In-process single-flight is a pure optimization; it is **not** correctness.

The refresh-token rate limiter is **DB-backed** (`critical:true`, keyed by IP + refresh-token-hash prefix), not an in-memory `Map`. In-memory `Map`s split brute-force attempts across N replicas; the refresh endpoint is the higher-value brute-force target (stolen refresh token) and must use the same `dbRateLimiter` primitive the device-flow leg uses.

### D4 — One deep module, ONE cascade branch, FUSED with the principal-binding seam

`src/opzava/core/auth/` (new, sibling to `core/{approvals,artifacts,secrets,workflows}`) is the deep module owning issuance/rotation/validation/revocation. Its public surface is small: `resolveDeviceToken(bearer): User | null` (the cascade branch), `issueForDevice(workspaceId, ...)`, `rotate(...)`, `revoke(...)`, plus pure `buildReviewPrompt`-style helpers for prompt/verdict and device-code. Its sole consumer in the cascade is the **one** `resolveDeviceToken` branch inserted between the `agent_api_keys` block (`auth.ts:505-554`) and the plugin hook (`auth.ts:557`). The branch is ~15 lines of cascade glue that delegates the lookup to `token-service.resolveDeviceToken`, which itself mirrors the agent-key block's steps faithfully: extract Bearer, `hashApiKey` sha256, `SELECT ... WHERE access_token_hash=? AND revoked_at IS NULL AND access_expires_at > (now - 60s)` (with the chain-level revoked check — see D2), stamp `last_seen_at`, `deriveRoleFromScopes(scopes)` defaulting to **viewer**, return a `User` carrying `agent_id`/`agent_name`/`workspace_id`/`device_session_id`.

**Fused with principal-binding (MASTER-PLAN task B1).** Device tokens are **principal-bound and scope-derived from day one**. Because `resolveDeviceToken` returns a `User` shaped identically to the agent-key path, the Track B principal-binding authz (`requireAgentSelfAccess`/`requireAgentTaskAccess`) governs device tokens identically to agent-scoped keys. To kill a latent circular dependency, the fuse point is **split**: B1a (principal-binding on the agent-mutating + bulk-task + lateral-movement routes, `depends_on:[]`) lands independently of B1b (the `resolveDeviceToken` cascade branch, `depends_on:[D2]`). `issueForDevice` **requires** an explicit `workspace_id` parameter (no `?? 1` default — closes the cross-tenant trap at both schema and code) and **rejects or downgrades** any scope that `deriveRoleFromScopes` maps to admin. Default scope is viewer/operator, **never admin** (contrast the global API key admin at `auth.ts:495`). An admin approving their own device still receives an operator/viewer token. Device-token-authenticated requests that reach the dispatch path still pass through `scanForInjection` (`agent-runtimes.ts`) — the device path adds no injection-guard bypass.

`device_tokens.workspace_id` is declared `INTEGER NOT NULL` in the schema (not merely "no default") so the resolved decision is enforced at the DB, not just in `issueForDevice`.

### D5 — Schema: migrations 055 → 058 + the `revoked_access_tokens` table

Two migrations land in this ARD's scope (renumbered from the original v1's `055` to avoid collisions — see MASTER-PLAN linearized order: A1=`055`, B2=`056`, A4=`057`, **D1=`058`**):

- **`058_device_tokens_oauth_sessions`** creates `device_tokens` (a near-clone of `agent_api_keys`/`040` at `migrations.ts:1224`, adding `rotation_chain_id`/`refresh_token_prev_hash`/`rotated_at`/`rotation_seq`/`access_expires_at`/`refresh_expires_at`/`audience`/`revoke_reason`; `workspace_id INTEGER NOT NULL`; `UNIQUE(workspace_id, access_token_hash)`, `UNIQUE(workspace_id, refresh_token_hash)`; indexes on `rotation_chain_id`/`user_id`/`device_id`/`refresh_token_hash`/`access_expires_at`/`revoked_at`) and `oauth_device_sessions` (the device-code approval queue, cloning the `access_requests` template). `device_tokens.audience TEXT` is **reserved now** (per D7 transport decision) to avoid a future migration. `audience` is populated but **not enforced** in the stdio-only state.
- **`059_revoked_access_tokens_denylist`** (GRILL-2 gap fix) creates the `revoked_access_tokens(access_token_hash TEXT PRIMARY KEY, revoked_at INTEGER, revoke_reason TEXT, rotation_chain_id TEXT, workspace_id INTEGER NOT NULL)` table referenced by D2's `MC_DEVICE_INSTANT_REVOKE` opt-in. Without this migration, the opt-in kill-switch runtime-fails on first revoke. Both migrations are idempotent (`CREATE TABLE IF NOT EXISTS`), and both are documented in `docs/architecture/system-map/00-database-ledger.md`.

The migration-array insertion point is the closing `]` of `migrations[]` (the array ends immediately before `runMigrations`); both migrations are appended there with `PRAGMA table_info` guards mirroring `054`.

### D6 — Local token store: `0o600` + optional envelope, no passphrase, no keytar

`0o600` plaintext local file + **optional** envelope encryption via `OPZAVA_TOKEN_ENC_KEY` (fallback `AUTH_SECRET` — both `randomBytes(32)`, `auto-credentials.ts:52-53`; default-on for the `refresh_token_prev_hash` rotation-chain columns). **No passphrase** — a headless stdio spawn has no TTY and cannot prompt; fail-closed passphrase either silently breaks every cold-start-after-reboot or collapses to the env-key path. **No keytar/libsecret** — deprecated/unmaintained since 2022, with a per-OS/node-version native rebuild that breaks Docker parity and the `node .next/standalone/server.js` single-binary contract (CLAUDE.md Pitfalls). The explicit plaintext opt-in is gated behind `OPZAVA_INSECURE_STORAGE` (default unset; set to `1` only to opt into plaintext). The shared `scripts/lib/mc-client.cjs` adapter (extracted in Track C, tasks C0/C4) is the **one** home for the credential store and writes via atomic temp+rename in the same directory as the target (a crash mid-refresh must not corrupt the only credential) at `0o600`. A **runtime-verified cold-start no-TTY invariant** holds: spawning the shim with a piped stdin and no credential file exits non-zero within a bounded timeout with an actionable `mc auth device` stderr line, never blocks on `stdin.read`.

### D7 — Transport: stdio-only now, HTTP-MCP deferred and additive

**Stdio-only now** (MCP 2025-06-18: stdio servers SHOULD NOT follow the auth spec). HTTP-MCP (RFC 9728 + RFC 8414 metadata + RFC 7591 dynamic client registration + mandatory PKCE + RFC 8707 resource indicators) is **deferred as additive** — the token endpoint is **grant-type-agnostic from day one** (it accepts `grant_type=refresh_token` and `grant_type=device_code`, and is structured to accept `grant_type=authorization_code` without a rewrite), and the `device_tokens.audience` column is reserved. Tracked as a future state, **not P0**. The resilient transport reuses existing primitives: the realtime SSE cursor (`realtime-events.ts:165` `readServerEventsAfter`, `:202` `parseLastEventId`) for server→client resume; the `client_message_id` idempotency precedent for exactly-once mutation retry (per-mutation `Idempotency-Key` partial-unique-index, migration-`054` pattern at `migrations.ts:1493`) — **honestly scoped** to routes that have an existing idempotency index (chat via `054`, task capture via MASTER-PLAN A1's `client_request_id`); non-indexed routes fall back to single-attempt-no-retry so a retry never silently double-writes. The one genuinely-new client work is the `sseStream` `Last-Event-ID` rewrite — verified gap at `mc-cli.cjs:207`/`:252`.

### TTL, grace, and skew

8h access / 30d rotating refresh. **60s** server-skew grace on access validation (accept an access token up to 60s past `access_expires_at`, absorbing client/server drift and letting an in-flight request complete at the boundary). **Zero** grace on the 30d refresh cap — refresh tokens hard-expire; this is a deliberate control, not drift tolerance. The client proactively refreshes at `access_expires_at - 60s`.

## Consequences

### Positive

- No permanent admin credential on operator disks; the global API key admin (`auth.ts:495`) is no longer the default agent-tool credential.
- Bounded 8h leaked-token blast radius; stolen-token detection with automatic family revocation (RFC 6749 §10.4); browser-driven human approval per device (RFC 8628 §5.4 anti-phishing); principal-bound from day one so device tokens are governed by the same authz as agent-scoped keys.
- One deep module behind one cascade branch — minimal structural entropy; the cascade stays shallow and the auth domain stays out of the shim/CLI (no shallow-module scatter).
- Reused primitives throughout (`safeCompare`, sha256 hashing, `deriveRoleFromScopes`, the `agent_api_keys` shape, the `access_requests` approval template, the SSE cursor, the `client_message_id` idempotency index) — the only new substrate is the `sseStream` client-resume rewrite.

### Negative

- **The 8h revoked-but-unexpired access-token window (residual risk #3).** Revocation is lazy for the stdio agent (next-call 401), not push — the SSE broadcast reaches the **dashboard** in near-real-time, but a stdio agent has no long-lived SSE connection. An attacker who stole a valid access token retains it up to 8h − 60s skew after an operator clicks revoke. **Mitigation:** the chain-level revoke (D2) kills tokens refreshed after the revoke immediately; the 8h bound caps the worst case; the `security.event` broadcast surfaces the revoke. Operators who demand instant kill on the *current* un-rotated access token can enable `MC_DEVICE_INSTANT_REVOKE=1` (the materialized denylist, O(1) per-request lookup at the cost of a per-request DB hit). This tolerance is the one product/policy call that benefits from a human sign-off — the knob makes the trade-off explicit rather than hidden. **Default: off** (honors the resolved decision).
- **The rotation-race guard is the highest subtle-bug surface.** Correctness hangs on the atomic `MAX(rotation_seq)` predicate (D3) and the multi-process concurrency test. A subtle defect here either false-revokes legitimate concurrent retries (the v1 hole) or silently swallows reuse (the row-level hole).
- **New migration and module surface.** Migrations `058`/`059` (two + one table); new module `src/opzava/core/auth/`; new routes `/api/auth/device/{code,token,revoke}`, `/api/auth/devices`, `/api/auth/devices/[id]/revoke`; new browser `/device` page; `architecture.test.ts` gains a `core/auth` layering + `resolveDeviceToken`-uniqueness guard.

### Couplings and invariants that MUST hold

- **Migration-id uniqueness** is guarded by the MASTER-PLAN A1 governance test (`test/migration-ids-unique.test.mjs`), which loads `migrations[]`, `extraMigrations[]`, **and** `getOpzavaRunnerMigrations()` (the runner migrations are runtime-injected via a side-effecting `registerOpzavaRunnerMigrations`, not a static import — the test must call it explicitly). `058`, `059`, and `opzava_runner_004` are all collectively guarded against collision.
- **SSE resume honesty (GRILL-2 red-team correction).** The `sseStream` rewrite resumes without gaps **for events persisted before the disconnect**. During a Dokploy zero-downtime redeploy with a leadership handoff (single-active-writer, ARD 0011 / MASTER-PLAN G1), the client may observe a **silence gap of up to lock TTL** for dispatch-generated events, because only the elected leader emits `task.status_changed` events — a read-only replica's dispatch chain is dormant. This window is documented in the ops-cheatsheet so an operator observing an SSE gap during redeploy does not chase a phantom bug.
- **Honest exactly-once scope.** Mutation retry via `Idempotency-Key` is supported **only** for routes with an existing idempotency index; other routes fall back to single-attempt-no-retry. A generic `idempotency_key` does **not** exist on most mutating tables — the v1 assumption was false.
- **Logging redaction is discipline, not enforcement** (`logger.ts` has no auto-redaction). A governance test greps every device-flow source line containing `logSecurityEvent|logAuditEvent|broadcast|throw|Error(` for raw `mc_dt_`/`mc_rt_`/`device_code=`/`refresh_token` patterns (anchored on the actual logging primitives, not just `console.*`). A positive control (inject `logSecurityEvent({detail: JSON.stringify({token:'mc_dt_xxx'})})`) must fail the test.

## Alternatives considered

- **Passphrase-encrypted local file (D1/D3 default).** Rejected as the primary path: a fail-closed passphrase in a headless stdio spawn with no TTY either silently breaks every cold-start-after-reboot or collapses to the `OPZAVA_TOKEN_ENC_KEY` env path — reducing to D2's opt-in envelope anyway. No passphrase is the decisive winner. (Passphrase is available only as a non-default if an operator explicitly opts into a TTY-bearing flow; it is not the shipped path.)
- **1h access TTL (D3).** Rejected: 24x the rotation-race exposure and DB write load for marginal leaked-token benefit over the 8h + chain-level-revoke + near-real-time broadcast set.
- **`gh` never-expiring tokens.** Rejected: no blast-radius bound, no rotation, no server-side revocation (gh `auth logout` only purges locally). The 8h/30d model is a deliberate divergence and a genuine improvement over gh.
- **OS keychain (keytar/libsecret).** Rejected: deprecated/unmaintained since 2022; per-OS/node-version native rebuild breaks Docker parity and the standalone binary contract. No keyring dependency.
- **HTTP-MCP from day one.** Rejected for this deliverable: stdio-first matches the MCP 2025-06-18 spec and the actual deployment topology; HTTP-MCP is additive because the token endpoint is grant-type-agnostic and the `audience` column is reserved. Deferred and tracked as a future state, not P0.
- **Row-level revocation (the naive reading of D2).** Rejected after GRILL-2 red-team: a stolen refresh token refreshed before the operator's revoke creates a new un-revoked row in the same chain; row-level revocation would honor the attacker's new access token for up to 8h. Chain-level revocation is the correctness property.

## Open questions for operator sign-off

The decisions above are FINAL and honored without re-litigation. The following are the residual tolerances that genuinely benefit from a human sign-off (engineering defaults are shipped as decided; the knobs make the trade-offs explicit):

1. **The 8h revoked-but-unexpired tolerance** — confirm operators accept that a stolen, already-issued access token is honored up to 8h − skew after a revoke, or whether the `MC_DEVICE_INSTANT_REVOKE=1` denylist should be on by default (cost: a per-request DB hit on every device-token-authenticated request).
2. **The SSE leadership-handoff silence gap** — confirm operators understand that dispatch-event SSE can go quiet for up to lock TTL during a Dokploy redeploy with a leadership handoff, so the gap is not mistaken for a bug.
